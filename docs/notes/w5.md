## Repair round 1 (review of W5a, 2026-11-07)
- **Security and HTTP:**
  - **Registration:** a WebSocket upgrade registers its connection only while its endpoint record is live. That check runs under the same lock as revocation, so a revoked URL never gets a live connection or a lease.
  - **Requests on revocation:** every HTTP request is counted on its record and runs under a context that revocation cancels. RevokeSession and Stop wait for the counted requests (round 2 bounds that wait; see below).
  - **Reservation owner:** it is read under the record lock, and each decision reads it once.
  - **Redaction:** every log line goes through one redaction step. It replaces the secret path parts after /t/, /e/ and /devtools/browser/ whether or not the token or record is still known. Round 2 also keeps client-chosen values out of the log (see below).
- **Targets and sessions:**
  - **Detach fence:** each attachment has its own context and fence. Detach fences the whole subtree, cancels and waits for its admitted work, then releases its state. A handler that holds an operation and then detaches its own session would deadlock; W5b handlers must not do that.
  - **Parent and child:** attach checks that the parent is live at start and again when the attachment is published, under the same lock.
  - **Auto-attach and discovery:** auto-attach off detaches the auto-attached sessions, and re-enabling replays the existing targets once. Discovery announces newly allowed targets once.
  - **By-value evaluate:** Runtime.evaluate with awaitPromise and returnByValue reads the value through Runtime.callFunctionOn, then releases the remote object; the expression runs only once.
- **Property tests:** TestEndpointLifecycleProperty (endpoint records, leases, redaction) and TestAttachmentLifetimeProperty (attachments, auto-attach, discovery).

## Repair round 2 (closure review of round 1, 2026-11-07)
- **Bounded revocation:**
  - Every HTTP response has a write deadline of writeTimeout (10 s) from its first byte (statusRecorder.begin). net/http clears it when the response ends, so it does not carry over to a later WebSocket upgrade on the same connection. Round 3 gives the upgrade's own HTTP 101 handshake a deadline (see below).
  - On revocation, drain closes the network connection of every admitted request whose response has started: such a request waits only for its client. A request whose response has not started still gets its answer (the cancelled action's error, 404 for an upgrade); the write deadline bounds that write. Page work still ends before RevokeSession and Stop return.
  - Tests: TestRevocationClosesStalledResponses (the review's 16 MiB title with a client that stops reading), TestStalledResponseWriteIsBounded, TestUpgradeAfterAResponseOnTheSameConnection.
- **Client values in the log:** no value that a client chooses is logged raw: header values (Origin, Host; Referer is not logged at all), a non-standard HTTP method, path segments other than the route words, and CDP method names that are not Domain.method of letters. The log shows "<value xxxxxxxx>" or "<method xxxxxxxx>", the first 8 hex digits of the value's SHA-256, so equal values can be matched. These markers are deterministic pseudonyms, not anonymization: equal values give the same marker in every line and every log, and a guessable low-entropy value (for example Origin null, always "<value 74234e98>") can be recovered by hashing candidates. They keep out only values that cannot be guessed, such as tokens and endpoint ids. The secret path positions keep their markers. Tests: TestClientValuesAreNeverLogged; TestEndpointLifecycleProperty now also sends current and retired secrets as Origin, Host and Referer.
- **Property scheduling:** a blocker of TestAttachmentLifetimeProperty also ends after blockHold (cleanupTimeout / 5) on a timer, because a synchronous step (autoAttach:false) can wait for it. Test: TestLifetimeBlockThenDisable (the review's five steps).
- **Not here:** the data race between core releaseRuntime and ensureAttached (unlocked title read) belongs to the core fix.

## Repair round 3 (closure review of round 2, 2026-11-07)
- **Bounded revocation includes the HTTP 101 handshake:** a WebSocket upgrade hijacks its connection, and Gorilla clears the connection's deadlines and writes the 101 response itself. Until conn.run owns the WebSocket, a revocation does not see that socket as a WebSocket connection. Round 2 therefore waited for a client that did not read the handshake.
  - The Upgrader's HandshakeTimeout is the response write time (writeTimeout, 10 s), so the handshake write is bounded like any HTTP response.
  - statusRecorder.Hijack hands the hijacked connection to Server.hijacked, which marks the request as writing. drain then closes that connection, so RevokeSession and Stop return at once. A hijack that comes after the record was revoked closes its connection itself, because drain may have read the record's requests already.
  - Unchanged: page work is cancelled and drained before RevokeSession and Stop return, and a revoked URL's upgrade gets 404.
  - Tests: TestRevocationClosesStalledHandshake (the review's reproduction, for RevokeSession and Stop, over a net.Pipe that never reads), TestStalledHandshakeIsBounded, TestHijackAfterRevocationCloses.

## W5b-1: Page, Runtime, Log and Performance (2026-11-08)
- **Event plumbing (internal/cdp/events.go):** each page attachment has a pageState (session.page, created in conn.attach, closed at detach before detachedFromTarget). It subscribes to every page event with the additive core.Manager.SubscribeOrdered (repair round 2): the handler runs in each connection's read loop and gets each event with its source target and its position (core.EventPosition: the delivering connection, its active target right after it read the event, and since repair round 5 the event's place in that connection's stream, Seq; events that a reconnect's new connection delivered before the swap keep the position at which they were read), and only queues it; one goroutine of the attachment handles the queue in order (internal/cdp/staging.go). Domain files register WIP event translators with onPageEvent(method, fn); fn runs under ps.mu in arrival order; ps.emitLocked(domain, ...) sends when the domain is enabled. W5c hook: use ps.loaderFor(target, wipLoader) as the requestId of the main-frame document request (requestId == loaderId), and call ps.noteNavigationLocked(loader) there to let Page.navigate return at the request.
- **Provisional targets (repair round 1, review F1; repair round 2, F1 and F5):** the events of a provisional target are staged in arrival order and translated only at its Target.didCommitProvisionalTarget, so a cross-process navigation publishes its document generation once, at the commit (contexts cleared, frameNavigated, the new contexts, then its other staged events, in their order); a target destroyed without a commit takes its staged events with it, and the active document, its contexts and Page.getFrameTree stay as they were. The commit signal is core's (the outer Target events of the same subscription, as DesiredState.followTargets and the scheduler's holds use them); there is no second tracker. Since repair round 2 an event is classified at its position, in the read loop: its target is provisional when it is not the delivering connection's active target right after that event was read, unless a Target.targetCreated announced it as no provisional target (a worker). So the classification needs no announcement (a provisional target created before the attachment, or a target of a new connection) and does not change when the attachment lags behind the connection across a commit (round 1 asked the connection's current active target when the attachment got to the event; review r1 F1). Frame, context, lifecycle and same-document events also count only from the target that reported the frame or document they name (reportedBy, frameOfLocked), because WIP numbers frames per process. W5c note: Network events of a provisional target are staged too once Network has translators and are translated at the commit, before the check for the target's document; a translator that must see the document request before the commit needs its own rule. Bounds and reset (repair round 2, F5): the attachment's queue holds at most 4096 events and 8 MiB of payload; the staged events of all provisional targets together at most 1024 events and 1 MiB, of at most 4 targets. Nothing incomplete is published: a target that exceeds the staging bounds loses its staged events, a fifth staged target pushes out the oldest (remembered as lost, 8 entries), and the commit of such a target publishes a reset instead; a full queue drops the later events until the attachment caught up, which then resets at once and again at the next commit. The first event of another connection (a reconnect) also resets, and forgets the staged targets as lost, because the page may have navigated while no connection delivered events. A reset is Runtime.executionContextsCleared at once, then the page's frame tree read in an operation of the attachment (10 s budget) and announced as a new document: frameNavigated of the main frame with a new loader id, the init lifecycle event, frameAttached and frameNavigated of each child frame, and with Runtime enabled the default contexts (and aliases) of the main frame and of each child frame that the connection has a context for. A tree read while the attachment changed its connection is not seeded (readTree). Repair round 3 (review r2): a commit whose staged events do not give the committed target's document (none staged, for example because the target reported its document before the attachment existed, or WebKit sends frameNavigated after the commit) resets too (F1); that reset keeps the remembered loader ids, because the committed target's documents have their own (target, loader) keys and a translator of its staged events may already have given the document its id (W5c's document request). All loss bookkeeping is bounded (F5): an overflowed target keeps its staging slot with a mark, so the marks are at most the 4 staged targets and go with them (destruction, commit, eviction, a new connection); when the 8-entry lost ring overwrites a target, the next commit resets (resetOnCommit), so a target is never forgotten as lost; at most 64 targets are remembered as no provisional ones (oldest forgotten first). Every other reset drops the remembered loader ids, so the announced document and its frames get new loader ids even when the page still shows the same WIP document (F7), and a tree read that a reset overtakes is not seeded (connSeq grows at each reset). After a reset the attachment has no document (ps.main is nil) until a tree read seeds it; Page.getFrameTree, getResourceTree, navigate and createIsolatedWorld check it under the lock of its use (documentLocked) and fail with a transient "retry the command" error (F6). After a reset, the new document's frameNavigated sends no second executionContextsCleared. A panic in a CDP handler or its Later becomes that command's error, with the stack in the daemon log, instead of ending the daemon (conn.handle). Repair rounds 4 to 6 (review r3, F9; review r4, F10; review r5, F11): every tree read is applied at the exact place of its reply in the attachment's event stream (staging.go "Tree reads"; readTree, the only seeding path, used by Page.enable, Runtime.enable, the Page handlers and the read after every reset: commit without a document, lost events, overflow, a new connection). WebKit sends a target's events and the replies to its commands in one ordered stream (iwdp: both in Target.dispatchMessageFromTarget; direct transport: the device's read loop hands one page's messages to a FIFO in order), and webkit.Session's read loop handles both in that order. readTree sends Page.getResourceTree with the additive core.WithReplyPosition (webkit.WithReplyHook underneath): when the session reads the successful reply, it calls the hook in its read loop, before it reads the next message, with the reply's position (core.EventPosition, now with Seq, the session's read count, webkit.Session.ReadPosition; events get the same Seq through SubscribeOrdered). The hook queues the reply as one more item of the attachment's queue; the goroutine applies the tree when it gets there (treeLocked), and readTree returns after that. So the events read before the reply are applied before the tree and the later ones after it, whatever documents they name: round 4 guessed the tree's place from its (target, loader) identity, which a back/forward restore repeats (F10), and its generations, the pre-read barrier and the discard of older generations are gone. Further rules: a reply of a target that is not the active one at its position (a commit replaced it) is not applied; a reply read on a new connection resets like that connection's first event, and its tree is not applied; a read that a reset overtook is still not applied (connSeq); a reply's bytes do not count against the queue's byte bound (the read holds them anyway), so a large tree cannot cause a loop of overflow resets. Round 6 (F11): round 5 discarded an event of an applied tree's connection with a lower Seq than the tree, because core's hand-over (pageConn.swap) delivered a new connection's held events while that connection already read, so a reply could overtake them; but a tree does not rebuild everything those events carry (a frame's removal, a child frame's navigation, contexts, console records).
