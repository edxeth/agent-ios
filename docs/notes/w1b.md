## Review repairs, round 6, core part (review w1b-repair5-closure-20261107-034003)
- R6-1: legacyCall's beginChange error was a short declaration (err) inside the if block, so the deferred `err = end(err)` set that shadowed local, and forwarding failures never reached the caller. It is now berr; the deferred end updates the named result.
- R6-2 per-item completion (chosen over per-target sync versions): every forwarded send queued for a provisional target is an item with its own result and done channel. A queue is sent in FIFO order, one item at a time, by whoever holds the target's sending slot: the setup (all of it; it returns the failures of the items it sent, so the Session marks the target's setup failed), or a change in end, which sends only up to its own last item and then frees the slot. Each change waits for all of its own items, whoever sends them, and returns their failures. An item whose target is gone, replaced by a new connection or a new setup, or whose setup failed, completes without error (the state went with the target, or ReapplySetup sends all of it). Changes still release d.chg before they wait, and setups never take d.chg, so the setup gate cannot deadlock against a change. ### core-events r3: the release and attach lifecycle (review P1 x2, last repair round)
- Causes (reviewer reproductions, /home/devkit/.pi/artifacts/reviewer/core-events-r2-repro/): (1) reattach and recover checked only `releasing` at the install, so a release that started and ended during a takeover's connect left a connection installed whose setup had sent the released session's state. The context replay runs as a change and checks Needs then.
- Removal without cleanup on a live connection (a change held the lock past the release deadline): the release reports the deadline (exit 124), the owners still leave the model, and the domains they touched become unknown (`d.unknown`). ### core-events r1: holds of a replaced target (decision)
- Question: iOS 16 and WebKitGTK 2.54 do not disconnect the replaced target's backend at commit (WebPageInspectorController::didCommitProvisionalPage only reports targetDestroyed; main sends DisconnectInspector). Is dropping its holds at didCommitProvisionalTarget still right?
- Decision: yes, keep dropping. (1) A page that is not cached is closed at the commit (WebPageProxy::commitProvisionalPage sends WebPage::Close unless the page was suspended); WebPage::close disconnects its frontends, and InspectorNetworkAgent::willDestroyFrontendAndBackend runs disable, which continues every pending intercept (continuePendingRequests/Responses, webkitgtk-2.54.2 InspectorNetworkAgent.cpp:898-910). (2) A cached page keeps its pending intercepts while it is cached (the agent removes an entry only when a completion takes it or on disable), but no completion can reach it: the target is destroyed and the session refuses every send to it, so a kept hold would only make the release barrier fail. (3) When the page is restored, its target is announced again and its setup resets the Network agent (resetCalls: Network is a state domain and is reset unless the record says disabled, and an unknown agent is reset), and that Network.disable continues every pending intercept before the page runs again, so no hold from before the commit is ever answerable through the daemon. On WebKitGTK 2.54.2 the old document's loads are also stopped when the navigation continues in another process (FrameLoader::continueLoadAfterNavigationPolicy, LoadWillContinueInAnotherProcess -> stopAllLoaders, FrameLoader.cpp:4232-4233), so such a hold mostly has a finished loader ("already processed"); iOS 16 (WebKit-7615.3.12) calls stopAllLoaders there only for StopAllLoads, which I did not trace further.

## Decisions and deviations so far
- D9 resolved the exit code: 124 for every expired deadline (legacy and registry).
- A free page of a physical device still needs a reservation (design 2.5 rule 1 is checked before the busy hint).
- Explicit ws:// URLs: loopback ports 9222-9322 are treated as physical iwdp pages that any reservation of the owner covers (the UDID is not known from the URL).
- commands.Env is unchanged; the daemon's Env offers Op() and Manager() through type assertion (adding Manager() to the interface would change W1a test fakes).
- /v1/run sends argv and re-parses it in the daemon instead of the {command, args, flags} body of design 2.2.
- D10: the daemon starts iwdp only through RunOptions.StartIWDP for the default listing address and never stops or restarts it; test binaries set it to nil.
- D10, iwdp start (after the first device smoke test, where a loaded host made the daemon start 50 copies while the user's iwdp still owned 9221): proxy.CheckListing is the one check for the daemon, proxy.IsRunning and proxy.Start. It decides ownership with a bind probe (bind without listen, SO_REUSEADDR so TIME_WAIT leftovers do not count, on every resolved address and on the wildcard address of its family); only a successful bind (ErrNotListening) allows a start. A refused connection proves nothing: a socket that is bound but does not listen refuses too. A process that owns the port but does not answer GET /json with 200 within proxy.ProbeBudget (5 s, shared) gets an error that names the address and says it is busy or stuck; no second iwdp is started. proxy.Starter (proxy.Start, EnsureRunning, the legacy iwdp_status auto-start and the binaries' StartIWDP) starts one process at a time, also across processes (a flock on iwdp-mcp-start-<uid>-<address>.lock in XDG_RUNTIME_DIR or the temporary directory), probes the address again after device discovery right before the spawn, and starts iwdp in its own process group. It accepts readiness only when the group owns the listening socket that receives a connection to the listing endpoint, address and port: the socket on the exact address wins, else the wildcard of its family (for IPv4 then a dual-stack [::]); another process's socket there means "another process took port N". On Linux the sockets, addresses and inodes come from /proc/net/tcp and tcp6, and a socket is the group's when its inode is among /proc/<pid>/fd of the group's processes. On darwin lsof -w -n -P -iTCP:<port> -sTCP:LISTEN -F pgtn lists each socket with its process group and address; it runs under the readiness context and at most 2 s, and is killed and reaped when either ends. lsof without root sees only this user's processes, so another user's listener counts as nobody and the start fails at its readiness wait. A failed check stops the group and fails the start. When another process's listener answers, it stops its group and reports "another process took port N"; when the wait fails or is cancelled it stops the group too (SIGTERM, SIGKILL after 2 s) and waits for the process to exit before it returns. A failed start is returned again without an attempt for proxy.StartBackoff (30 s); a cancelled one, or one that lost the port to another process, is not. Tests: internal/proxy/start_test.go (fake iwdp on PATH, private loopback addresses) and internal/daemon/iwdp_start_test.go. proxy.Restart and restart_iwdp are unchanged: Restart still runs "pkill -x ios_webkit_debug_proxy", which stops every iwdp of the user, and its Start now also refuses while the old process owns the port and honors the back-off.
- Owners of a session end with ":<session>" (core.SessionOwner); release finds them by that suffix.
