## Actions and event tasks (design 3.5, 2.6)
- Every action step is an attempt of the daemon's attempt loop (core.RunSteps). The page function `act` (js/50) is async; runtime.RuntimeCaller calls it by reference and reads the envelope with Runtime.awaitPromise (`asyncFns` in internal/runtime/runtime.go). An immediate object answer (a refused owner) is read with Runtime.callFunctionOn, because WebKit refuses Runtime.awaitPromise for a non-promise.
- Events are grouped as real input groups them: the events of one native input event (mouse move, mouse down, mouse up, key down, key up, touch) run in one task, each after a microtask turn (`_.ev`). Two native input events are separated by `_.gap`: a timer of delay 0, then a MessageChannel hop; between mouse down and mouse up the gap also waits for the next animation frame (at most 50 ms). Deviation from the literal "one task per event": events of one native input event share a task, as in a browser. The fixture with a mousedown handler that queues a microtask and a task passes in real input order (TestActionClickRunsPageTasksBetweenEvents).
- Every event and default action first checks `x.live()` (attempt end, deadline, cancel, epoch); a step stopped in the middle answers "interrupted". The fence rules of 2.6 and 7.3 test 4 hold.
- type without --delay sends 8 characters per step, so a step fits its 250 ms attempt window.
- Core change (internal/core/attempt.go): RunSteps keeps the reason of the page's last retry, so "click" names "covered by <div ...>" (attempt_reason_w3b_test.go). `Action.Reserve` and `ErrActionTimeout`: no attempt is sent, and no attempt window reaches, past deadline minus the reserve, so the last reply arrives inside the command deadline. Actions use 250 ms, or a quarter of the remaining time for short deadlines; an element that never becomes ready fails with ErrActionTimeout (exit 124) and its last retry reason. This also fixed the `go test -race ./internal/commands` failure (a covered click that ended as "canceled; outcome unknown").
- Action timeout: action commands have Command.Timeout 5 s (design 3.5 default); type and keyboard keep 30 s because of --delay.
- A target the page refuses (ambiguous, stale or unknown ref, bad selector) fails at once with the runtime error; a missing element is retried until the deadline.
- Every result says the input was synthetic and names any emulated default action.
- Headless MiniBrowser never has system focus, so WebKit fires no focus event there; the click test checks document.activeElement instead.
- click --new-tab (repair round 1) is one fenced attempt step (kind newtab, js/55-actions.js) with click's checks; --force skips them. Each attempt makes two runtime calls: actProbe (the attempt's checks only, without a user gesture; a ready element answers retry "ready to dispatch") and then, only after a ready probe, actGesture: the same attempt in a Runtime.evaluate with emulateUserGesture, which runs window.open synchronously. Since repair round 2 the attempt loop sends them as two attempts (core.Action.Probe and core.ProbeReady; action.Gesture in commands/w3b_page.go), and actGesture gets a window sized from the measured round trip (below, "Repair round 2", item 6). So an attempt that has to wait gives the page no user activation. Remaining race (not fixed): when the page changes between the probe and the gesture call (the link becomes covered or moves), the gesture call answers retry after it has already granted the page a user activation; no window opens, but the page saw an activation it would not get from a real user.
- tap <x> <y> keeps the requested point for every touch, pointer and mouse event; tap <target> uses the element center. keydown and press --phase down send only keydown; keyup and press --phase up apply the Space activation only after a matching uncanceled keydown of the same key on the same target (state per owner, cleared by an owner reset and a release). Enter activates links and buttons only; checkboxes and radios activate on Space (design 3.5).
- hover --css (W3b-R1-merge). WebKit applies CSS.forcePseudoState only while the CSS domain is enabled and only when it is set after CSS.enable; CSS.disable removes its effect (probe on WebKitGTK: /home/devkit/.pi/artifacts/worker/w3b-evidence/w3b-r1-merge/probe-webkitgtk-css-domain.log). Before the merge the command printed "CSS :hover forced" without the effect, because webkit.Session refused CSS.enable on every transport. Now:
  - transport.Limits.CSSDomain says that an endpoint answers CSS.enable, CSS.getAllStyleSheets and CSS.getStyleSheetText. Only the WebKitGTK transport sets it; webkit.Session refuses the three methods without a write unless it is set (through iwdp they hang and stall the connection; the direct transport is not checked on a device, so it is refused too).
  - Where CSS.enable is refused (iwdp, direct), `hover --css` fails with exit 2 and the reason before any event, as design 4.3 does for impossible features. Without --css, hover works on every transport.
  - Where it is answered (WebKitGTK), the session's hover owner holds the CSS domain in the desired state (CSS.enable for the first owner), then forces :hover on the node. The next action or the release resets the forced state and disables the domain when no other owner holds it. A CSS.enable with an unknown outcome (lost reply) keeps the domain with the owner, so the next action or the release disables it.
  - Tests: TestActionHoverCSS and TestActionHoverCSSThroughTheDaemon (WebKitGTK, in process and through the daemon and separate CLI processes: the #hov:hover color is applied, and the next action resets it), TestHoverCSSForcesAndClearsThePseudoState, TestHoverCSSEnableFailures, TestHoverCSSFailedHoverStillReleasesTheDomain, TestHoverCSSFailsWhereCSSEnableIsRefused (commands), TestSessionSendsCSSMethodsOnlyWhereTheEndpointAnswersThem (webkit).
  - The legacy MCP CSS tools and Manager.Raw still refuse these methods on every Target-routed connection; this change does not touch them.

## Waits (design 3.6)
- wait has Command.Timeout 25 s plus a 150 ms reserve: a wait ends 150 ms before the command deadline with exit 3 and the last state. `--fn` evaluates `!!(expr)` with Runtime.evaluate (not subject to CSP). `wait --url` survives a cross-site process swap (TestWaitFormsOnWebKitGTK counts the swap from Target.didCommitProvisionalTarget).
- `wait --load networkidle` waits in the daemon on W4's network tracker (devtools.WaitNetworkIdle): no request in flight for 500 ms (devtools.DefaultIdleQuiet). In the daemon the lease hooks start the session's network capture with the first registry command, so the wait normally finds it running; when the wait has to start it, the result says that requests that began earlier were not seen. A wait that ends first exits 3 and names the number of requests still in flight. Tests: internal/commands/wait_networkidle_test.go, TestWaitNetworkIdleOnWebKitGTK (a fetch to the fixture's /slow endpoint holds the wait).

## Dialogs (design 3.7)
- The bridge is activated by the first action or dialog command of a session: bootstrap part "dialog" at core.RankDialog and the Console owner dialog:<session>. Both are set in one DesiredState.Change (activateDialogs), so a provisional target whose setup already ran before the change gets the bootstrap part and the Console owner before it commits (TestDialogBridgeReachesAProvisionalTarget in internal/commands/dialog_change_test.go). Answers are issued by the dialog command and before each action; uses are acknowledged only by page replies (the action's step value or a "dialogs" call). The console.debug marker is telemetry only; no Go code reads it.
- An issued answer that the page neither holds nor reported used expires, and the next result says "dialog answer <id> expired with its document". A new lease epoch (release, takeover) drops queued answers and expires issued ones, so a takeover never writes an answer again.
- open, back and forward withdraw unused answers in the call that starts the navigation; reload withdraws in a first phase and sends Page.reload only after its reply (or after its 1 s budget when the reply is lost; the answers then expire).
- Item 7 (b), lost acknowledgment (TestDialogLostAcknowledgmentOnWebKitGTK): the test hook drops the click's awaited reply (the act envelope that reports the use of d1) and the marker event, waits until the fixture records the accepted confirm, then closes the page connection. The click fails; a command without --takeover gets the lost-page error; `click --takeover` reattaches, its confirm in the same document returns false and its result reports "dialog answer d1 expired with its document"; a confirm in a new cross-origin document also returns false; the fixture records the accept in exactly one document. Red logs (deliberate mutations of dialogBridge.newEpoch, reverted): /home/devkit/.pi/artifacts/worker/w3b-evidence/w3b-3/red-7b-mutA-requeue.log (an issued answer requeued at takeover is written again: "confirm:true") and red-7b-mutB-silent-expiry.log (expiry not reported).
- Per-session W3b state is keyed by a weak pointer to the page record's ref table and dropped with it (runtime.AddCleanup); it outlives leases, so answers of an earlier lease are reported as expired.

## Navigation, tabs, frames, screenshots, find (W3b-2a)
- open: one runtime call ("dialogs" with withdraw and nav) withdraws the unused answers and sets location.href (1 s budget; a lost reply is accepted and the withdrawn answers expire). It then waits for a new document generation or a changed URL, then the load state (--wait load|domcontentloaded|none), then issues queued answers into the new document. Page.navigate is never sent (WebKitGTK has none).
- URL schemes (W3b-R1-merge). CLI open follows agent-browser's open (cli/src/commands.rs normalize_navigation_url, commit 6682da3): a URL that starts with http://, https://, about:, data: or file: (any case) is used as given; every other URL gets https:// in front (a.test/x, localhost:8080, 127.0.0.1:8080/path, [::1]:8080), so open never runs script through location.href. The normalized URL must parse (Go net/url); javascript:alert(1) becomes https://javascript:alert(1), whose port "alert(1)" is invalid, so open refuses it with exit 2 before any page call (repair round 2). agent-browser also keeps chrome:// and chrome-extension://, which WebKit does not have. The MCP tool navigate keeps the rule of the legacy tool (design 4.1, same meaning): only http and https URLs, with the legacy errors "unsupported URL scheme ...; only http and https are allowed" and "invalid URL: ..."; a URL without a scheme is refused as before. The check is Command.MCPCheck, which mcpInput runs for MCP calls only (TestNavigateMCPAcceptsOnlyHTTPAndHTTPS, TestOpenNormalizesURLsLikeAgentBrowser with a property over generated URLs, TestNavigateThroughMCPRefusesNonWebSchemes).
- back and forward: the same call with hist -1 or 1. pushstate: the Next.js router if present, else history.pushState and popstate.
- Tab discovery (design 2.5 rule 4, review finding 1) lists the pages of a physical device only for the owner of a live reservation; others are left out and counted.
- wait @eN --state detached|hidden is satisfied when the ref's element was removed (review finding 4).
- MCP reload takes the legacy ignore_cache (review finding 2).
- Tabs: core keeps tab ids t1, t2, ... per page key for the daemon's life, labels, and each session's current page (internal/core/pages_w3b.go; one hunk in Manager.touch resolves every request through sessionPage). `tab <id>` probes the page (2 s), makes it current and releases the session's leases on other pages; a failed probe says "tab tN is not the visible Safari tab; bring it to the front on the device". tab new: window.open with a user gesture, then the list is polled every 250 ms for 10 s; the new tab becomes current. tab close: window.close(), wait up to 3 s for the page to leave the list. MiniBrowser lists window.open windows, so these run on WebKitGTK; the hidden-tab probe is tested with the fake.
- Tab state is a package map keyed by *Manager, not a Manager field, to keep manager.go to one hunk; entries of closed managers are never dropped. "session release" does not clear the session's current page (session.go is W1's).
- Core additions for frame scoping (repair round 1): internal/core/exec_context_w3b.go adds Op.SetExecutionContext and Op.ExecutionContext; an operation with a context adds contextId to each Runtime.evaluate it sends and addresses every send to the context's reporting target and connection (opCaller and attemptCaller in scheduler.go send through op.route; Op.exec holds a core.ExecContext; see "Final repair round 1"). The attempt clock mappings (scheduler.go clocks, attempt.go measureClock and RunSteps) are keyed by clockKey, the document generation and the execution context, because a frame's performance.now() has its own time origin.
- frame (review finding 3; see also "Repair round 2" items 1 and 2): "frame <iframe>" makes the frame's execution context the session's scope (per session, lease epoch and top document); later runtime commands (snapshot, get, is, find, wait, actions) send their Runtime.evaluate calls there (core.Op SetExecutionContext; clock mappings per generation and context). The frame id comes from the iframe's index in window.frames and Page.getResourceTree; the context from Runtime.executionContextCreated (the frame owner holds the Runtime domain). Navigation commands and screenshot work on the top document; a navigation ends the scope; "frame main" ends it and releases Runtime. A frame without a context in the page's target is unsupported. eval stays in the top document. Same-origin and cross-origin frames pass on WebKitGTK (TestFrameScopesLaterCommandsOnWebKitGTK).
- screenshot (registry): legacy forms (path or -o, --full-page, --selector css) plus --full, --selector @eN, --annotate, --if-changed. --annotate always takes a new snapshot; with --selector the labels cover only refs that intersect the element's box, and the capture is Page.snapshotRect of that box (snapshotNode would not paint the overlay). When the operation ended before the overlay was removed (deadline, cancel), a fenced cleanup operation of the same session and epoch removes it; an owner reset also removes it. MCP tool take_screenshot is this command (legacy full_page, selector; new annotate, if_changed); the MCP binding returns the PNG as image content (up to 3.75 MB) with the text and file_path. --format and --quality are not implemented.
- find ... <action>: click, dblclick, tap, hover, focus, check, uncheck, scrollintoview, fill <text>, type <text>, on exactly one match, under find's 30 s deadline; action flags are not passed.

## Final round (W3b-final)

1. Frame context inventory (round-4 review findings P1 and P2). The scheduler no longer subscribes to Runtime.executionContextCreated and Page.frameDetached and no longer captures a new connection's reports (Scheduler.captureContexts is gone). It reads the connection's own inventory, webkit.Session.ExecutionContexts of the active target, which the session's read loop records from the session's creation on, also during a provisional target's setup (contextSource in internal/core/exec_context_w3b.go). A reconnect turns each recorded context into its frame id (contextsMoved), and a release looks the frame's newest main-world context up on the current connection when it sends; it never keeps or sends an id of an earlier connection. The wait reads the inventory's completeness before the frames' contexts and checks its context again after both reads, so neither a report that lands between the reads nor a cancel just before them makes a live frame gone (both seen once under `go test -race`; the subtests "reported between the reads" and "canceled before the inventory read" reproduce them deterministically). The WebKitGTK reconnect tests (navigation_reconnect_test.go) close the connection from the tap, which is a peer end: the page is lost and the command passes --takeover, as 9d requires.
4. New test: TestRetiredReleaseWriteKeepsTheFrameRecord (internal/core/exec_context_retired_w3b_test.go). A frame release whose socket write fails retires the connection, on a webkit.Client (a write timeout and a broken write) and on a webkit.Session (a write timeout in the WebSocket's own write). The failed release carries no ErrNotSent and sets no write notice, so ForgetFailedExecutionContexts keeps the frame record; after the reconnect, the next release releases the frame in its context on the new connection. Setting the notice on a failed write fails it for each connection kind (mutation-client-notice-on-retired-write.log, mutation-session-notice-on-retired-write.log).

## Repair round 2 (W3b-R2: the round-1 delta reviews)
Evidence: /home/devkit/.pi/artifacts/worker/w3b-evidence/w3b-r2/ (red-*.log before the fix, green-*.log after it, mutation-*.log).
1. Frame contexts and release (design 2.4, 3.7). Before, the lease release ran the page-side runtime release only in the main context, so a dialog override installed through "frame" stayed in the frame.
