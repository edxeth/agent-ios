# W3a wiring into the daemon (notes for W6)

Design: docs/design/agentic-parity.md, sections 2.5, 2.9, 3.1 and 3.3. This wires the "Hooks for W3a" of docs/notes/w1b.md and the "What W1b must wire" list of docs/notes/w3a.md.

## What is wired
- Daemon id: every page session carries `PageSession.DaemonID` = `ManagerOptions.DaemonID` (the daemon's random id from `newDaemonID` in `newCore`, also `Hello.ID`). The W3a commands use it as `runtime.Owner.Daemon` (`setOwnerFromLease`); "" falls back to the process-wide `runtime.DaemonID` (page sessions built outside a manager, as in the W3a test harnesses). The global `runtime.DaemonID` is not changed: the IWDP_NO_DAEMON core can start again in the same process, with epochs from 1, so the id must belong to the manager.
- `Manager.ensureAttached` creates `runtime.New(pc, pc.Generation)` and `refs.NewTable()` with the page record, and `SchedulerOptions.Runtime = rt.RuntimeCaller()`.
- Ref table per page record, not per session: the page keeps one set of ref maps per document, held by one lease owner at a time. The table mirrors them: an owner change resets the page maps, the reset report clears the table (`NoteReset`), and its counter never moves back, so ref ids are not handed out twice while the record lives. Both live on the swappable page connection, so they survive reconnects of the same lease (design 3.3).
- Bootstrap part `runtime` (`core.RuntimePart`, `core.RankRuntime`, source `runtime.Source()`), owned by the page (owner "runtime", not ":<session>"), so release keeps it. Consequence: every first attach now sends `Page.enable` and `Page.setBootstrapScript` (about 51 KB on the wire), also for explicit ws:// URLs and the legacy mock. `Page.enable` also gives the session its document generations (frameNavigated), which `stale_ref` needs.
- Lease epochs come from one manager-wide counter (`Manager.epochs`), so they grow across sessions, releases and page records within one daemon id. Before, the per-record counter started again at 1 after the sweeper closed an idle record, and the page refused the new owner with `stale_owner`.

- Runtime calls of a command go through its operation (design 2.5, 2.10): `openRuntime` binds the page runtime to `Op.Caller()` with `runtime.Runtime.Via` when the Env has `Op() *core.Op` (the daemon's `runEnv`). The bound runtime shares the owner, its confirmation and the reset reports with the page runtime, so concurrent reads never swap a shared caller. Each call counts against the per-page limit of 8 protocol calls in flight and is refused before sending once the operation ended or its lease epoch changed.
- Snapshot history per logical session: `refs.Table` keeps the last two snapshots per session (`RecordSnapshot(session, text)`, `Snapshots(session)`), the session being the lease holder that runs the command. The table itself stays per page record. The history keeps the snapshots of a session across its leases (the command contract is "the last two snapshots of this session"); it grows with the sessions that took a snapshot on the page and goes away with the page record (IdleClose).
- The runtime part keeps the Page domain enabled: a bootstrap part is a requirement of Page like an owner (`DesiredState.Needs`, W1b), and the runtime part is never removed, so a legacy `Page.disable`, a legacy owner's disable and the release of the last Page owner send nothing (design 2.4 reference count), and the bootstrap part keeps working (design 3.1 install path 2). The runtime is not a separate Page owner: with the `Needs` rule that owner changed nothing on the wire (the tests pass with and without it), so it was dropped when the wiring moved onto the final W1b.
- The runtime part is set on the new desired state before the first connection opens. Every setup snapshot has it, also that of a provisional target created while the first connection applies the state. No target exists yet when it is set, so it needs no desired-state change (`beginChange`), which forwards changes to provisional targets with older snapshots. Setting it on the live state after the connection opened would miss such a target (TestProvisionalTargetDuringAttachGetsThePageRuntime fails that way). WebKit source (researcher report /home/devkit/.pi/artifacts/researcher/webkit-bootstrap-page-disable-20261107.md, WebKit main 456c5d1 and the iOS 16-era tags 7615.3.12, 7615.1.26, 7614.1.14): `Page.disable` keeps `m_bootstrapScript` but clears `enabledPageAgent`, and `didClearWindowObjectInWorld`, which evaluates the script, runs only for an enabled Page agent. So documents created while Page is disabled get no runtime; `Page.enable` brings injection back without a resend. This was read from source, not run on a device.
- Lease end runs the page-side release: the release barrier's cleanup calls `runtime.Runtime.Release(ctx, c, epoch)` on the control caller after the desired-state cleanup (`releaseOwners`), for explicit release, lease break, idle expiry and shutdown (all go through `Manager.releasePage`). The call carries no owner and is fenced by the epoch in the page (`release(epoch)` in js/10-core.js does nothing when its owner has another epoch). It does not install a missing runtime. A lost page gets no release (no reconnect for cleanup, design 2.4).
- Release budget rule (`Manager.releaseRuntime`): the desired-state cleanup is required and runs first; the runtime release is best effort and waits at most `min(runtimeReleaseBudget = 1 s, time left before the release deadline - runtimeReleaseReserve = 50 ms)`. With less than `runtimeReleaseMin = 10 ms` of that left it is skipped and logged. A skip or failure is logged only, and the release succeeds: the next owner's first runtime call resets the page maps anyway (design 3.1). The reserve keeps time for ending the lease and for the reply to reach the client before the client's own deadline: the client sends its remaining time as timeoutMs, so the daemon's deadline is later than the client's by the transit time, which is far below 50 ms on the local socket. The minimum is below any realistic answer time of a runtime call (warm eval p50 13.8 ms through the CLI). Before this rule the runtime release ran first with the whole remaining deadline: a release with timeoutMs 150 and a silent page runtime returned exit 124 and never sent Network.disable (review w3a-wiring-repair-r1).
- Ordering check for cleanup first: the release barrier (`Scheduler.Release`) continues held requests, resumes a paused debugger and resumes targets paused on start before any cleanup, so a session that left the page at a breakpoint is resumed before both the cleanup and the runtime release's `Runtime.evaluate`. The cleanup then removes the session's breakpoints and disables domains it alone held; `Runtime.evaluate` needs neither Debugger nor Runtime enabled, and Page stays enabled because the runtime part needs it. The cleanup re-sends the bootstrap script without the session's parts, but the runtime part is the page's and stays. A Network reset inside the cleanup closes and reopens admission within the release barrier and does not touch page JavaScript. Running the runtime release last means its hooks restore (dialog overrides, fetch/XHR patches of W3b) after the session's Console owner may be gone, so the page's `console.debug` telemetry of that restore can be missed; that telemetry is not proof of anything (design 3.7). No other ordering dependency was found.

## Tests
- internal/commands/runtime_fence_test.go: runtime calls of a command are refused after its operation ended and after the lease epoch changed.
- internal/daemon/runtime_repair_test.go: 12 concurrent `get title` with held replies put at most 8 runtime calls on the page; session B's first `diff snapshot` after A's two snapshots and release finds no snapshot.
- internal/core/runtime_repair_test.go: legacy Page.disable, enable/disable and release never disable Page; lease end (release, idle expiry, shutdown) sends `release` with the lease epoch; a release with an error envelope or a lost reply still ends the lease and cleans up the desired state; an owner's cancellation of a release during the runtime release ends the lease after the cleanup and does not stall the page (W1b close-probe rule).
- internal/refs/refs_test.go: the snapshot history is per session.
- internal/core/runtime_wiring_test.go: recreated record never reuses an epoch; epochs-only-grow property (testing/quick); attach wires runtime, refs, daemon id, scheduler runtime caller and the page-owned bootstrap part; a provisional target created during the first attach gets Page.enable and the runtime part before it commits.
- internal/daemon/runtime_wiring_test.go: snapshot and a later `get text @e1` from another client run in the daemon and carry the hello id as owner daemon.
- e2e/webkitgtk/daemon_runtime_test.go: on WebKitGTK through the daemon, `snapshot` then `get text @eN` in a later CLI process; after `lease break` session B gets "no snapshot produced @eN"; A under a new epoch too; a new snapshot gives a higher id.

## Open points
- Ref ids are not reused when a table is new while the page still holds refs of an earlier owner (daemon restart, or a page record recreated after IdleClose): the page allocates `max(alloc.next, maxRef + 1)` (js/10-core.js `refFor`), and `maxRef` survives resets. An earlier note here claimed otherwise; the review refuted it.
- The page-side release is fenced by the epoch only, not by the daemon id (the page API is `release(epoch)`): a release from this daemon whose epoch equals the epoch of another daemon's current owner clears that owner's maps. That owner's next call then reports the refs as unknown; no ref resolves to a wrong element.
- A takeover (`--takeover`) reattaches a lost page; the lost lease got no page-side release (design 2.4: no reconnect for cleanup), so the new owner's first runtime call resets the page maps.
