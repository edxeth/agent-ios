# Known limits

Every accepted limit of this release, with its reason. Features that iOS WebKit cannot support at all are in [synthetic-input.md](synthetic-input.md). Ids in brackets (K01, C13, ...) refer to the W1c backlog and [notes/w1c.md](notes/w1c.md).

## Ownership and connections

- **Reservations and busy hints are not locks.** A client that ignores reservations (another tool, a raw script, Safari Web Inspector) can still take a page. Reason: iwdp gives a page to the newest client, and with `--no-frontend` it reports no owner.
- **A peer-ended first attach (F13).** When another client ends the daemon's very first connection to a page, the daemon has no page state to mark lost. The next first attach is decided by the preflight busy hint only.
- **"Stalled" wording after a peer end.** A call whose own budget ended and whose probe then finds the connection ended by a peer can still report a stall instead of "lost" (exit 4 either way). `tab <id>` gives the takeover advice only when the page is already marked lost; otherwise it gives the hidden-tab advice. The CDP `Target.activateTarget` probe says "not the visible Safari tab" for any probe failure.
- **iwdp does not list pages while a page is connected.** On the second device check, the user's iwdp (1.9.2) closed every listing request on 9221 and 9224 without a reply while any WebSocket to a page was open, and answered again after it closed. The cause is unknown (iwdp's source has no such rule). Commands on a page that the daemon holds open need no listing: the session's page without `--page` (the `tab <id>` choice, else the page its last command without `--page` used), its tab id or key, or its ws:// URL. Commands that need the listing (`tab list`, `tab new`, `tab close`, `tab <id>` for a page that is not attached, `--page <title>`, another session's first command, `pages`, `devices`, the CDP endpoint's page list) fail with exit 5 and advice: run `iwdp-cli daemon stop` to close the page connections, or restart that iwdp. The same holds when the device list answers but the page list of a device with an open page fails; a device without an open page whose page list fails is left out, as before, so it hides no other device. The daemon never takes such an iwdp for dead and never starts a second one. The legacy `pages`, `devices` and `status` run outside the daemon, so they name the empty reply and its likely cause, not the open connection. MCP `iwdp_status` still reports "failed to start iwdp" with the check's error in this case, although it starts nothing.
  - **CDP clients on such an iwdp.** The CDP endpoint reads the listing for its target list and for every target lookup (`/json/list`, a `/devtools/page/...` connection, `Target.getTargets`, `setAutoAttach`, `attachToTarget`, and others), so these fail with the same advice while the daemon holds any page connection, also one that an earlier CLI command opened. `get cdp-url` itself reads no listing when it selects a page that the daemon holds open (the session's `tab` choice, its default page, or `--page` with its tab id, label, key or ws:// URL), but a client of the URL still needs the listing for its target list. What to do: run `iwdp-cli daemon stop` (it also stops the CDP endpoint and revokes its URLs) or restart that iwdp, then get a new URL. Whether a CDP client can work on such an iwdp at all is not known, because its own attachment opens a page connection. Details: [cdp.md](cdp.md#when-iwdp-does-not-list-pages).
- **A command during a recovery** waits for the running background reconnect within its deadline; it never waits for a lost page, which needs `--takeover`.
- **iwdp start (K01).** The check that port 9221 is free is a bind probe, not an atomic reservation, so a short window remains between the check and the start. On macOS `lsof` sees only this user's processes.
- **restart_iwdp on macOS.** The restart refuses unless it can read both the process start time (`ps`, one-second resolution) and the start token from the kernel's process arguments. `make sim-teardown` on macOS always refuses and prints `kill <pid>`. On every system the identity check and the signal are separate system calls.
- **Reconnect events.** A reconnect's new connection holds at most 1024 events per subscriber until it is installed; extra queued events are dropped and counted, and a read-loop overflow refuses the connection (exit 4).
- **Idle probe (K08).** An idle probe that the client cancels resets the idle clock, so the next command within the idle period runs without a probe; its call budget still detects a hang.
- **Writes after a stall (K09).** After a stall is declared, a write that starts in a narrow window can still block until its own deadline.
- **Two daemons on one page.** The page-side release of the runtime checks the lease epoch only, not the daemon. A release from one daemon whose epoch equals the epoch of another daemon's current owner clears that owner's ref maps, and that owner's next call reports its refs as unknown. No ref resolves to a wrong element. Reason: the page runtime's release takes only an epoch (`release(epoch)`).

## Page state and cleanup

- **No reconnect only to clean up.** When a lease ends without a live connection, or its cleanup fails, page-side state stays until the document navigates: the geolocation shim, JavaScript-mode routes and dialog overrides of the current document (C18). A cleanup that is owed is sent by the next connection's setup, or by a bounded background reset after a provisional target commits.
- **Release does not undo the page.** It does not restore authentication state or undo submitted forms or transactions.
- **Profiler stop (C19).** On a stall, `profiler stop` ends at its deadline (exit 124) instead of at once with exit 4. A ScriptProfiler run left on a connection that was not attached is not marked; WebKit ends it when that connection closes, otherwise the next start stops it.
- **Back/forward cache.** Forced pseudo states and DOM node bindings of a cached document survive a restore (K06; inert without `CSS.enable`). A request paused in a cached page stays paused until restore or eviction, and a restore whose setup fails before its `Network.disable` leaves it unknown to the daemon (K05). The context list of a restored document fills one or two round trips after its navigation event; on iOS 16 nothing is replayed unless Page is enabled (K11).
- **Agent bookkeeping (K10).** Two concurrent first enables of one agent on one target can interleave their resets. Agent records of replaced targets stay for the life of the connection.
- **Breakpoints.** A breakpoint set that crosses a provisional commit can fail with a target-swapped error; a retry succeeds (K07). The breakpoint id recorded for a target that was destroyed can stay in the desired state until the next setup replaces it.
- **Debugger pauses.** A pause that arrives after a release ended its lease is not drained. A release that cannot resume every paused target names them in its error. Pause records stay until their target is destroyed.
- **Node ids in the main document.** A command that looks up a node id and then sends it (`hover --css`, `highlight`, a screenshot of a ref) has no target fence in the main document. When a provisional target commits between the lookup and the send, the node id goes to the new document, where it can name another node or none. Reason: only a frame scope (`frame <iframe>`) pins the sends of a command to the target that reported its execution context; inside a frame such a send is refused instead.
- **Frame cleanup wait.** A frame whose page-side state an earlier lease left is counted as gone only on a complete context inventory of the current target (Runtime known to be enabled there). Until then the frame stays recorded, and each runtime command of the new lease waits for the frame's report again, at most 250 ms and half of its 1 s cleanup budget, until the inventory is complete or the lease release runs. Reason: a frame that the inventory does not list yet can still exist and hold state.
- **Network gaps (K02, K03).** A gap in the network log starts when the old connection was retired; events that a stalled connection never delivered before that are outside the gap. When the old frontend's close already reset Network and the new setup sent no `Network.disable`, the gap is reported only by a later connection that sends one.
- **Refused intercepted requests (K04).** A request that WebKit took and then refused (decode error, finished loader) stays unanswered inside WebKit.
- **Safety net (K12).** A page used only by legacy commands has no interception safety net. Tombstones of removed interception rules end with the lease: a provisional target that refused a rule's removal and commits after the release keeps the rule. A rule that a provisional target kept after it refused a removal that the daemon sent itself (a lease release, a legacy removal) has no tombstone either. In both cases the safety net answers the rule's requests, so no request stays paused.

## Explicit ws:// URLs (C13 to C16)

Pages opened by an explicit `ws://` URL (legacy commands with a ws-url argument, `IWDP_WS_URL`, MCP `select_page` with a URL) still use the older connection type. Reason: moving it onto the session layer changes the target-wait rules under every legacy mock test, so it needs its own change. Such pages have no agent resets of unknown backends (C14), report no source target for events (C15), and do not replay execution contexts after a back/forward cache restore, so `frame` after such a restore fails with an actionable error (C16). Such a connection has no agent states, so its context inventory never counts as complete, and a frame release there never decides that a frame is gone: the frame stays recorded.

## MCP profiles

- **Network and console lists in the default `core` profile.** In `core` alone (the default), `list_network_requests`, `get_console_messages` and `clear_console` are the legacy handlers, not the daemon's network log and console buffer. The older `list_network_requests` and `get_console_messages` list only what `network_enable` and `console_enable` captured, and these two tools are not in `core`, so both lists are always empty there: an empty list is no evidence that the page sent no request or logged nothing. The older `list_network_requests` is also not masked: it returns full URLs with their query tokens and request headers such as `Authorization`. With `core,legacy` the enable tools exist, but the lists stay the legacy, unmasked handlers. Reason: the registry tools of these names, with the capture that starts with the session's lease and the masking, are in the `devtools` profile (decision D2), and `core` keeps the legacy tools of these names without their enable tools. Workaround: select a profile with `devtools`, for example `IWDP_MCP_TOOLS=core,devtools` or `iwdp-mcp --tools core,devtools`, or `all`. [migration.md](migration.md#mcp-server) lists which handler serves which tool in each profile.

## Features and platforms

- **Pause-on-start is best effort.** "Runs before page scripts" (dialog override, init scripts, error hooks, JavaScript routes) is partial when WebKit refuses pause-on-start or does not answer within 1 s. Not yet verified through iwdp on a device.
- **One ScriptProfiler recording per page.** `profiler start`, `trace start` with the `script` category (the default categories are `timeline,script`) and a legacy `ScriptProfiler.startTracking` all use WebKit's one ScriptProfiler run of the page. While one of them records, a second start is refused and names what to do: stop the recording that holds the run (`profiler stop`, `trace stop`), or start the trace with `--categories timeline`. To trace and profile at the same time, record a Timeline-only trace (`trace start --categories timeline`) beside the profiler. Reason: WebKit runs at most one ScriptProfiler run per page, and a second `ScriptProfiler.startTracking` starts nothing, so the second recording would silently share the first one's samples.
- **CSS through iwdp.** `CSS.enable`, `CSS.getAllStyleSheets` and `CSS.getStyleSheetText` hang through iwdp and are refused; `hover --css` therefore fails there.
- **Not verified on a device:** see [Open device questions](#open-device-questions).
- **Storage quota.** `state load` and `state save` refuse a storage area above 90% of the 5 MiB quota in WebKit's count; strings that page script stored as 16-bit can count less than WebKit counts.
- **`diff screenshot`** compares viewport screenshots only. **`vitals`**: LCP, CLS and INP need Safari 26.2 or later.
- **`click --new-tab`.** When the page changes between the readiness probe and the gesture call, the page can hold a transient user activation although no tab opened.
- **Direct transport.** Results above the frame cap (default 256 MiB) need chunked messages, which are not supported: use `--transport iwdp`. On iOS 17 and later it may need a tunnel; until a device run passes, `auto` never chooses it.
- **CDP.** The endpoint serves the methods of the table in [cdp.md](cdp.md#method-table) and answers every other method with "wasn't found"; [cdp.md](cdp.md#limits-per-domain) lists the limits per domain and what each pinned client loses. The compatibility suite runs only on WebKitGTK. An endpoint under `IWDP_NO_DAEMON=1` ends with its process.
- **Whitespace text in the CDP accessibility tree.** `Accessibility.getFullAXTree` has a StaticText node named " " for each whitespace-only text node between elements, which Chrome leaves out. Clients show them: chrome-devtools-mcp's `take_snapshot` lists them as lines such as `uid=1_3 " "`, and Puppeteer's `accessibility.snapshot()` as extra StaticText leaves. The elements, their names and their uids or refs are not affected. Reason: the endpoint builds the tree from the runtime's snapshot walk (internal/runtime/js/40-snapshot.js), which collapses such text to one space and keeps it.

## Open device questions

No physical-device run has checked these yet. Each needs a device run before the behavior counts as verified.

- **Listing.** Why the user's iwdp (1.9.2) closes every listing request while a page WebSocket is open, and whether a CDP client can work on such an iwdp (see "iwdp does not list pages while a page is connected").
- **Pause-on-start.** Whether iwdp relays the reply of `Target.setPauseOnStart`; iOS 26 may hold it.
- **CDP clients.** No scenario of the compatibility suite has run against Safari on a device; the suite runs on WebKitGTK only.
- **Oversized sources.** iwdp's real outgoing limit to Safari on iOS 16.7 (64 MiB as configured, not measured), and the direct transport's (go-ios frame limit 16 MiB): send Playwright's injected script (330,312 characters) as one `Runtime.evaluate` through each. If both pass, that script needs no staging on iOS; larger sources can still reach the configured limits and be staged. If one fails, that transport's limit must be set to the measured value. Also whether a staged evaluate works on iOS 16.7 on a page whose Content-Security-Policy forbids eval.
- **Cookie delete.** Whether an expired `Page.setCookie` on iOS (NSHTTPCookieStorage) deletes exactly the cookie of that name, domain (with or without the dot) and path, keeps the namesakes of another path, of the parent domain and of the other kind, and whether the `Page.getCookies` right after it already shows the change. CDP `Network.deleteCookies`, `cookies clear` and `state load` depend on it. The cookie behavior of `cookies set` on iOS is not verified either.
- **ScriptProfiler.** Sampling on iOS (`profiler start`, CDP `Profiler`, and traces with script or V8 categories).
- **Interception.** Network interception in general; for CDP `Fetch`, the WIP rule texts with the bridge's NUL suffix on iOS 16.7 and current iOS, and the interception of a cross-process navigation's document request through iwdp.
- **Network conditions.** Whether the device's WebKit applies `Network.setEmulatedConditions` as its command list says (the lists of iOS 16.4 to 17.x and 27.3 and later have it). CDP `emulateNetworkConditions` and `emulate network` depend on it.
- **Other features:** `set credentials` (enabled on WebKitGTK only), touch events, and the direct transport.
