# Known limits

Every accepted limit of this release, with its reason. Features that iOS WebKit cannot support at all are in [synthetic-input.md](synthetic-input.md). Ids in brackets (K01, C13, ...) refer to the W1c backlog and [notes/w1c.md](notes/w1c.md).

## Ownership and connections

- **Reservations and busy hints are not locks.** A client that ignores reservations (another tool, a raw script, Safari Web Inspector) can still take a page. Reason: iwdp gives a page to the newest client, and with `--no-frontend` it reports no owner.
- **A peer-ended first attach (F13).** When another client ends the daemon's very first connection to a page, the daemon has no page state to mark lost. The next first attach is decided by the preflight busy hint only.
- **"Stalled" wording after a peer end.** A call whose own budget ended and whose probe then finds the connection ended by a peer can still report a stall instead of "lost" (exit 4 either way). `tab <id>` gives the takeover advice only when the page is already marked lost; otherwise it gives the hidden-tab advice. The CDP `Target.activateTarget` probe says "not the visible Safari tab" for any probe failure.
- **iwdp does not list pages while a page is connected.** On the second device check, the user's iwdp (1.9.2) closed every listing request on 9221 and 9224 without a reply while any WebSocket to a page was open, and answered again after it closed. Cause (device check 3): iwdp 1.9.2 can get one broken file-descriptor slot, right after the stderr pair "sendq retry failed: Connection timed out" and "recv failed: Bad file descriptor". Every connection that lands on that slot is closed without an answer; with one page WebSocket on the lowest free slot, every listing request lands on the broken one. Restart iwdp to recover: `agent-ios restart-iwdp` for an iwdp that agent-ios started; any other iwdp only whoever started it, and only when nobody else uses it: `scripts/iwdp-owner-check.sh --terminate <record>`, then `scripts/iwdp-owner-check.sh <record>` until it reports `gone`, as [Stopping an iwdp by hand](device-runbook.md#stopping-an-iwdp-by-hand) in device-runbook.md describes; otherwise ask whoever started it, or the user. Trigger (reproduced without a device): at start iwdp connects a SIMULATOR inspector to `localhost:27753` and tries each address of `localhost` in turn. When nothing listens on 27753, a `127.0.0.1` attempt is refused at once and iwdp goes on to the next address, so the order of the addresses does not matter: where `::1` is one of them and does not answer (for example IPv6 off on `lo`), the connect to `::1` stays pending, and about 133 s after each start iwdp removes it but keeps its send queue, which breaks that slot. Workaround: `-s 127.0.0.1:27753` gives iwdp one address, whose connect is refused at once. An iwdp that agent-ios starts (auto-start, `restart-iwdp`) passes this flag on Linux, where no iOS Simulator runs; macOS keeps the default address, which the simulator uses. For an iwdp that you start yourself on Linux, add `-s 127.0.0.1:27753` to its command line. v1.9.2 is the newest iwdp release and has no fix. Commands on attached pages keep working. Commands on a page that the daemon holds open need no listing: the session's page without `--page` (the `tab <id>` choice, else the page its last command without `--page` used), its tab id or key, or its ws:// URL. Commands that need the listing (`tab list`, `tab close`, `tab <id>` for a page that is not attached, `--page <title>`, another session's first command, `devices`, the CDP endpoint's page list) fail with exit 5 and advice: run `agent-ios daemon stop` to close the page connections, or restart that iwdp as above. `tab new` and `click --new-tab` still call `window.open` on the session's attached page, but the session stays on the opener with a warning that names this error (exit 0). The same holds when the device list answers but the page list of a device with an open page fails; a device without an open page whose page list fails is left out, as before, so it hides no other device. The daemon never takes such an iwdp for dead and never starts a second one. The commands `devices` and `status` read the listing themselves (`status` outside the daemon, `devices` in it), so they name the empty reply and its likely cause, not the open connection. `agent-ios status` reports the check's error with its advice ("does not answer: ..."); it starts nothing.
  - **CDP clients on such an iwdp.** The CDP endpoint reads the listing for its target list and for every target lookup (`/json/list`, a `/devtools/page/...` connection, `Target.getTargets`, `setAutoAttach`, `attachToTarget`, and others), so these fail with the same advice while the daemon holds any page connection, also one that an earlier CLI command opened. `get cdp-url` itself reads no listing when it selects a page that the daemon holds open (the session's `tab` choice, its default page, or `--page` with its tab id, label, key or ws:// URL), but a client of the URL still needs the listing for its target list. What to do: run `agent-ios daemon stop` (it also stops the CDP endpoint and revokes its URLs) or restart that iwdp as above, then get a new URL. Whether a CDP client can work on such an iwdp at all is not known, because its own attachment opens a page connection. Details: [cdp.md](cdp.md#when-iwdp-does-not-list-pages).
- **sim up's lease check is not a lock.** Before a restart of iwdp, `sim up` counts the daemon's active page leases on every device, before it changes the forward and again right before the restart, and refuses while there is one (docs/simulator.md). A session that takes a lease between that last count and the restart loses its page connection, as after `restart-iwdp`. Reason: the daemon has no request that holds new leases back during a restart of iwdp; adding one would change every page command's admission for this one rare case.
- **sim's forward is identified, then signaled.** `sim up` and `sim down` check the forward's pid, start time and start token right before SIGTERM, in separate system calls, as restart-iwdp does: a process that ends and whose pid is reused in that window could get the signal.
- **A command during a recovery** waits for the running background reconnect within its deadline; it never waits for a lost page, which needs `--takeover`.
- **iwdp loses the devices when usbmuxd restarts.** ios_webkit_debug_proxy 1.9.2 subscribes to usbmuxd's device events once and never subscribes again; its handler of a closed subscription does nothing, and no later upstream release changes that (upstream issue #28). Where usbmuxd exits when the last device is unplugged (Linux with `usbmuxd --systemd`), every iwdp that runs across an unplug lists no device from then on. On Linux the daemon restarts the iwdp that agent-ios started and recorded when it holds no usbmuxd connection any more ([guide.md](guide.md#the-daemon)); an iwdp of another user cannot be inspected and is left alone without a message; an iwdp that the user or another program started stays deaf until its owner restarts it, and the error says so. Device check of 2026-11-11: after a replug the old iwdp listed no device, and the next `tab list` restarted it and listed the tabs in 0.6 s; after another replug the restarted iwdp did not answer within 5 s and logged nothing about the device, and the command 30 s later started a new iwdp that listed the tabs.
- **iwdp drops a device when a client closes at the wrong moment.** ios_webkit_debug_proxy 1.9.2 ends its whole connection to a device when it fails to pass one inspector message (a reply or an event) to a page WebSocket that is closing or gone: `iwdp_on_applicationSentData` returns the failed send, and `rpc_recv_msg` then logs "Invalid message _rpc_applicationSentData" and closes the device connection. It never connects to that device again by itself. Device check of 2026-11-12: after iwdp ended a page connection while a reply to it was on its way, the iwdp log had that line and "Disconnected :9224 from iPhone X", and the listing stayed empty while `idevice_id -l` listed the iPhone. A raw WebSocket client reproduced it: it took a page that the daemon held, made the page log to the console every millisecond, and closed its socket with a reset; iwdp logged "send failed: Connection reset by peer", the "Invalid message" line and the disconnect. Every client that closes a page connection while the page still sends can cause it; agent-ios releases a page (Console.disable and the other resets) before it closes the connection, which leaves only the replies and events that are already on their way. On Linux the daemon and `devices` restart the iwdp that agent-ios started and recorded, at most once per 30 s ([guide.md](guide.md#the-daemon)); the device refused the first restart right after the loss, and accepted one 30 s later. Another program's iwdp stays without the device until its owner restarts it, and the error says so. In the same check, the first connection of about every second attach to a page that no other client held ended, with no message in iwdp's log; the command failed with exit 4 and told to run it again, which then attached. This was probably the fragmentation bug of the next point (the same exit 4 during the re-apply of the page state, with nothing in iwdp's log), which agent-ios now avoids; that check's logs were not kept, so this is not proven.
- **iwdp 1.9.2 mixes up the fragmentation state of both directions.** ios_webkit_debug_proxy keeps one "message in progress" flag per WebSocket (`continued_opcode` in websocket.c) for what it receives and what it sends. While a client's fragmented message is half received, iwdp sends every reply and event on that connection as a continuation frame; a client rejects it ("websocket: continuation after FIN"), and the page connection ends (exit 4, "closed the new connection during the re-apply of the page state"). When a device reply then reaches the closed socket, iwdp drops the whole device (previous point). agent-ios therefore never fragments: every message to a page leaves as one WebSocket frame, whatever its size (up to the 64 MiB limit of iwdp), and pongs and close frames go between messages, never inside one. Device check of 2026-11-26 (iPhone X, iOS 16.7.16): five `click --new-tab` in a row, with the daemon slowed by strace, failed this way in 2 of 2 chains with the earlier build (13 such errors) and in 0 of 6 chains with single frames, plus 3 chains without strace, 100 `eval` with a 7 KB expression and 10 chrome-devtools-mcp fill and click rounds without an error. Other clients of the same iwdp that fragment (gorilla/websocket splits client messages above 4096 bytes by default) still hit it. Reason: an upstream bug in the newest iwdp release; agent-ios does not bundle or patch iwdp.
- **The 30 s start back-off lives in one daemon's memory.** Without `AGENT_IOS_NO_DAEMON=1`, the daemon is the only process that starts iwdp by itself (page commands and `devices` run in it), so its back-off after a failed start covers every automatic start of that daemon. It does not hold across processes that do not share that daemon: with `AGENT_IOS_NO_DAEMON=1` every command has its own; processes with different `XDG_RUNTIME_DIR` values have different daemons; a client of another agent-ios binary replaces an idle daemon, which then starts without the old one's back-off; and a daemon killed while iwdp starts leaves that iwdp running, with no lock or record, while the next start may launch another. With `AGENT_IOS_NO_DAEMON=1` every command that needs iwdp can start it again, so repeated commands repeat the start (the reviewer's check of 2026-11-12: three `devices` commands, three failed starts in 0.4 s); in the other cases the new daemon or process starts without the back-off of the one before. A second iwdp does not start while the first one owns the listing port. Accepted by the user on 2026-11-12, after a cross-process back-off file kept needing more machinery for these cases.
- **A device that connects slowly or refuses at an iwdp start.** iwdp 1.9.2 listens on its listing port first and connects each USB device (lockdownd handshake, the Web Inspector service, TLS) inside its one event loop, so its listing does not answer during that connection. agent-ios waits up to 20 s from the start for an iwdp that listens (within the command's deadline), and keeps an iwdp that still has not answered running and recorded, also when the command's deadline ends first: the command fails with "kept running and recorded" (exit 1, or 124 at the deadline; `sim up` waits up to 30 s more for the listing instead); run it again in a moment, and `restart-iwdp` only when it stays unanswered. A device that refuses the inspector connection (a locked device) is not listed by that iwdp, and iwdp does not try it again later: unlock the device, then `restart-iwdp` (or unplug and plug it in). "Unable to connect to ..." lines that follow a stop of iwdp are its own shutdown message (it logs them for every device whose inspector had not answered yet), not a refusal.
- **iwdp start (K01).** The check that port 9221 is free is a bind probe, not an atomic reservation, so a short window remains between the check and the start. On macOS `lsof` sees only this user's processes.
- **restart-iwdp on macOS.** The restart refuses unless it can read both the process start time (`ps`, one-second resolution) and the start token from the kernel's process arguments. `scripts/iwdp-owner-check.sh --terminate` (Simulator teardown, manual stop) signals on Linux through a pidfd held during its checks; on macOS it sends SIGTERM by pid right after its checks, so a process that exits and whose pid is reused in that window could get it. restart-iwdp checks and signals in separate system calls on every system.
- **A Simulator iwdp record can outlive its process.** Teardown removes setup's iwdp record only when no process has the recorded pid. When a process of another user, or one with another start time, has reused that pid, the check reports `cannot-check` or `mismatch`, teardown keeps the record, and setup refuses until that process ends; the next teardown then removes the record.
- **Record removal compares, then deletes.** `scripts/iwdp-owner-check.sh --forget` (Simulator teardown, manual stop) renames a record aside, compares its device, inode and content with what it read, and deletes it only on a match. A writer that already holds the record open can still change it in place after that comparison. scripts/sim-setup.sh and agent-ios replace their records by rename and never write one in place.
- **Reconnect events.** A reconnect's new connection holds at most 1024 events per subscriber until it is installed; extra queued events are dropped and counted, and a read-loop overflow refuses the connection (exit 4).
- **Idle probe (K08).** An idle probe that the client cancels resets the idle clock, so the next command within the idle period runs without a probe; its call budget still detects a hang.
- **Writes after a stall (K09).** After a stall is declared, a write that starts in a narrow window can still block until its own deadline.
- **Two daemons on one page.** The page-side release of the runtime checks the lease epoch only, not the daemon. A release from one daemon whose epoch equals the epoch of another daemon's current owner clears that owner's ref maps, and that owner's next call reports its refs as unknown. No ref resolves to a wrong element. Reason: the page runtime's release takes only an epoch (`release(epoch)`).

## Page state and cleanup

- **No reconnect only to clean up.** When a lease ends without a live connection, or its cleanup fails, page-side state stays until the document navigates: the geolocation shim, JavaScript-mode routes and dialog overrides of the current document (C18). A cleanup that is owed is sent by the next connection's setup, or by a bounded background reset after a provisional target commits.
- **Release does not undo the page.** It does not restore authentication state or undo submitted forms or transactions.
- **Profiler stop (C19).** On a stall, `profiler stop` ends at its deadline (exit 124) instead of at once with exit 4. A ScriptProfiler run left on a connection that was not attached is not marked; WebKit ends it when that connection closes, otherwise the next start stops it.
- **Back/forward cache.** Forced pseudo states and DOM node bindings of a cached document survive a restore (K06; inert without `CSS.enable`). A request paused in a cached page stays paused until restore or eviction, and a restore whose setup fails before its `Network.disable` leaves it unknown to the daemon (K05). The context list of a restored document fills one or two round trips after its navigation event; on iOS 16 nothing is replayed unless Page is enabled (K11).
- **Agent bookkeeping (K10).** Two concurrent first enables of one agent on one target can interleave their resets. Agent records of replaced targets stay for the life of the connection.
- **Breakpoints.** A breakpoint set that crosses a provisional commit can fail with a target-swapped error; a retry succeeds (K07). The breakpoint id recorded for a target that was destroyed can stay in the desired state until the next setup replaces it.
- **Debugger pauses.** A pause that arrives after a release ended its lease is not drained. A release that cannot resume every paused target names them in its error. Pause records stay until their target is destroyed.
- **Node ids in the main document.** A command that looks up a node id and then sends it (`hover --css`, `highlight`, a screenshot of a ref) has no target fence in the main document. When a provisional target commits between the lookup and the send, the node id goes to the new document, where it can name another node or none. Reason: only a frame scope (`frame <iframe>`) pins the sends of a command to the target that reported its execution context; inside a frame such a send is refused instead.
- **Frame cleanup wait.** A frame whose page-side state an earlier lease left is counted as gone only on a complete context inventory of the current target (Runtime known to be enabled there). Until then the frame stays recorded, and each runtime command of the new lease waits for the frame's report again, at most 250 ms and half of its 1 s cleanup budget, until the inventory is complete or the lease release runs. Reason: a frame that the inventory does not list yet can still exist and hold state.
- **Network gaps (K02, K03).** A gap in the network log starts when the old connection was retired; events that a stalled connection never delivered before that are outside the gap. When the old frontend's close already reset Network and the new setup sent no `Network.disable`, the gap is reported only by a later connection that sends one.
- **Refused intercepted requests (K04).** A request that WebKit took and then refused (decode error, finished loader) stays unanswered inside WebKit.
- **Safety net (K12).** Tombstones of removed interception rules end with the lease: a provisional target that refused a rule's removal and commits after the release keeps the rule. A rule that a provisional target kept after it refused a removal that the daemon sent itself (for example a lease release) has no tombstone either. In both cases the safety net answers the rule's requests, so no request stays paused.

## Explicit ws:// URLs (C13 to C16)

Pages opened by an explicit `ws://` URL that is not an iwdp device page (`--page ws://...` for a local endpoint) still use the older connection type (`webkit.Client`). Reason: moving it onto the session layer changes the target-wait rules under every mock test that opens such a URL, so it needs its own change. Such pages have no agent resets of unknown backends (C14), report no source target for events (C15), and do not replay execution contexts after a back/forward cache restore, so `frame` after such a restore fails with an actionable error (C16). Such a connection has no agent states, so its context inventory never counts as complete, and a frame release there never decides that a frame is gone: the frame stays recorded.

## Features and platforms

- **Pause-on-start is best effort.** "Runs before page scripts" (dialog override, init scripts, error hooks, JavaScript routes, the CDP page compatibility shims) is partial when WebKit refuses pause-on-start or does not answer within 1 s. On iOS 16.7 through iwdp it probably works (device check 3, an inference: see "Open device questions").
- **document.cookie keeps deleted cookies.** In an open page, `document.cookie` still returns a cookie that WebKit deleted (an expired `Page.setCookie`, `cookies clear`), also after a reload and after a cross-site round trip, while the server and `Page.getCookies` no longer see it (device check 3, iOS 16.7). A non-expired `Page.setCookie` of the same cookie does update `document.cookie`. Inference: the web content process keeps a cookie cache that is not told about the deletion. Workaround: a page-side `document.cookie = "<name>=; expires=Thu, 01 Jan 1970 00:00:00 GMT; path=<path>"`.
- **Playwright locators on Safari below 17.4.** Playwright's locator actions, `getByRole` and `ariaSnapshot` call `Element.prototype.checkVisibility`, which Safari 16.6 (iOS 16.7) lacks; the CDP endpoint installs a shim for it, and Playwright's popover and `getHTML` features still fail ([cdp.md](cdp.md#page-compatibility-shims)). With the shim, device check 4 (iOS 16.7, code a8aec70) passed Playwright's `getByRole` click, `getByLabel` fill, a locator read and `ariaSnapshot`.
- **One ScriptProfiler recording per page.** `profiler start`, `trace start` with the `script` category (the default categories are `timeline,script`) and a CDP client's `Profiler.start` all use WebKit's one ScriptProfiler run of the page. While one of them records, a second start is refused and names what to do: stop the recording that holds the run (`profiler stop`, `trace stop`), or start the trace with `--categories timeline`. To trace and profile at the same time, record a Timeline-only trace (`trace start --categories timeline`) beside the profiler. Reason: WebKit runs at most one ScriptProfiler run per page, and a second `ScriptProfiler.startTracking` starts nothing, so the second recording would silently share the first one's samples.
- **CSS through iwdp.** `CSS.enable`, `CSS.getAllStyleSheets` and `CSS.getStyleSheetText` hang through iwdp and are never sent there (the CDP endpoint answers `CSS.enable` itself and refuses the other two); `hover --css` therefore fails there. `css matched` and `css computed` need none of them (see "CSS rules" below).
- **Not verified on a device:** see [Open device questions](#open-device-questions).
- **Storage quota.** `state load` and `state save` refuse a storage area above 90% of the 5 MiB quota in WebKit's count; strings that page script stored as 16-bit can count less than WebKit counts.
- **`diff screenshot`** compares viewport screenshots only. **`vitals`**: LCP, CLS and INP need Safari 26.2 or later.
- **`click --new-tab` and `tab new`.** When the page changes between click's readiness probe and the gesture call, the page can hold a transient user activation although no tab opened. The session follows the new tab, which is found as the first tab of the opener's device that the page list of that device did not have right before the `window.open` call: a tab that the user or another client opens on that device between that listing and the end of the wait for the new tab can be taken for it. When that listing fails, the session stays on the opener with a warning, also when the new tab opened: agent-ios does not guess the new tab by its URL. A browser that does not list script-opened windows leaves the session on the opener: `tab new` fails with exit 5 after 10 s; `click --new-tab` warns when the wait ends: after 10 s, or 0.5 s before the command deadline when that comes first (with the default 5 s action deadline, what the checks left, less 0.5 s).
- **Background tabs run no animation frames.** iOS Safari stops `requestAnimationFrame` in a tab behind another tab (iOS 16.7: `click` on such an opener waited for "the element to be stable" until its deadline). The stable check then samples the element's box 50 ms apart by a timer, so it does not wait forever; what the hidden page itself does (timers, its own animations) stays throttled by Safari.
- **Direct transport.** Results above the frame cap (default 256 MiB) need chunked messages, which are not supported: use `--transport iwdp`. On iOS 17 and later it may need a tunnel; until a device run passes, `auto` never chooses it.
- **CDP.** The endpoint serves the methods of the table in [cdp.md](cdp.md#method-table) and answers every other method with "wasn't found"; [cdp.md](cdp.md#limits-per-domain) lists the limits per domain and what each pinned client loses. The compatibility suite runs only on WebKitGTK. An endpoint under `AGENT_IOS_NO_DAEMON=1` ends with its process.
- **Network throttling and other emulation through CDP.** CPU throttling above rate 1, a transparent screenshot background (`omitBackground`), per-URL network conditions (rules that give some URLs other conditions than the rest), `navigator.onLine` and `navigator.connection` emulation and upload throttling cannot be emulated through the CDP endpoint ([cdp.md](cdp.md#limits-per-domain)). Network throttling works on iOS 16.4 to 17.x (download only) and on iOS 27.3 (download and latency); iOS 18.0 to 27.2 have no throttling, and a throttle there is refused before any change. chrome-devtools-mcp's `emulate` network presets (Slow 3G, Fast 3G and the others) all carry an upload limit, so the endpoint refuses each of them as a whole instead of applying only the download part, so that a client never believes it got a throttle it did not get; its `Offline` works. `forced-colors: active` and `prefers-contrast: less` or `custom` have no WIP user preference and are refused.
- **chrome-devtools-mcp tools without a WIP route.** `configure_webauthn` (WIP has no WebAuthn domain), `resize_page` (the viewport is fixed), `lighthouse_audit` (it needs device metrics and CPU throttling), `screencast_start` (iOS sends no screencast frames), `new_page` with `isolatedContext` (no browser contexts) and `take_heapsnapshot` with its heap analysis tools (HeapProfiler is not translated: WebKit's `Heap.snapshot` is JavaScriptCore's format, not V8's; use `agent-ios heap snapshot`) fail with the method's "wasn't found" answer or the reason.
- **Whitespace text in the CDP accessibility tree.** `Accessibility.getFullAXTree` has a StaticText node named " " for each whitespace-only text node between elements, which Chrome leaves out. Clients show them: chrome-devtools-mcp's `take_snapshot` lists them as lines such as `uid=1_3 " "`, and Puppeteer's `accessibility.snapshot()` as extra StaticText leaves. The elements, their names and their uids or refs are not affected. Reason: the endpoint builds the tree from the runtime's snapshot walk (internal/runtime/js/40-snapshot.js), which collapses such text to one space and keeps it.

## agent-browser 0.45 and chrome-devtools-mcp 1.14 features

Input and actions:

- **Modified clicks on links stay in the tab.** A modified synthetic click on a link (`click --modifiers control`, meta, shift or alt, or `press Control+Enter` on a focused link) is followed by WebKit in the same tab (checked on WebKitGTK for all four modifiers); Chrome would open a new tab or window. Use `click --new-tab` or `tab new <url>`. Not checked on iOS Safari.
- The back and forward buttons send their events (button 3 and 4, auxclick) but do not move in history.
- Held modifiers (`keydown Shift`) end with the document (navigation, reload) and with a new owner; agent-browser keeps them until its browser closes.
- Unknown key names and unknown chord modifiers stay usage errors (agent-browser sends an unknown name as key and code with keyCode 0); F-keys are not named keys.
- With the focus inside a cross-origin frame, keyboard commands without a target (`press`, `keydown`, `keyup`, `keyboard type|inserttext`, `type <text>`) are refused with `unsupported`: select that frame first (`frame <selector>`).
- drag works within one document (the page, or one same-origin frame); a drag between documents is refused with `unsupported`.
- A press interrupted mid-chord (attempt deadline) does not send the keyups of chord modifiers already pressed; a chord does not change the held modifiers, so no modifier stays held.
- agent-ios dispatches synthetic events to the target element itself, so a stale press point cannot click another element (agent-browser 0.45 fixed real CDP input that landed elsewhere, #2587 and #2611). The point still matters for the receives-events check and for the clientX and clientY that the page sees; it is measured after the layout settled.
- The action wait differs from agent-browser 0.45: no "up to 5 settle rounds, then press anyway" and no "re-scroll at most twice": agent-ios retries until the action deadline and fails with the last reason. hover keeps the receives-events check (agent-browser's hover only scrolls and settles). The error wording stays agent-ios's (`... stopped before step 1 of 1 (0 acknowledged): covered by <div id="banner">`).

Forms:

- **Form refusals have no JSON envelope.** agent-browser's `--json` error carries the code in `"code"`; agent-ios prints errors on stderr only, so the code is the prefix of the error line (`Error: select: option_not_found: ...`), in text and with `--json`.
- fill does not apply `maxlength`: it sets the value through the native setter, which a browser does not cut, and agent-browser's `value_truncated` warning is not given.
- `type --clear` is not implemented, and type gives no read-back warnings (`value_mismatch`, `effect_not_observed`).
- `select` on a native `<select>` sets the options, runs the `input` and `change` handlers (inside `dispatchEvent`) and reads the selection back in the same task as its call, so a change handler that navigates cannot lose the command's reply (20 of 20 runs on the iOS 26.5 Simulator). A page that changes the selection later (in a timer, a promise or a later task) is not detected: `select` then reports the requested options and gives no "holds a different value" warning. ARIA comboboxes and listboxes keep their two steps.
- Every `act` attempt of an action and every `wait` costs two round trips: one arms the reply (a promise in the page that is awaited before the call is sent), one runs the call; this is what keeps the reply of a click on a link or of a navigating change handler on the iOS Simulator (about 40 ms per round trip). A probe (`click --new-tab`) costs one. A document replaced between the arm and the call gives "the call ran in a newer document than the one its reply was armed in" (exit 1, the step may have run).
- The option list of `option_not_found` is bounded in the number of options and the length of each text, then "... and N more"; agent-browser prints every option in full.
- A custom combobox select runs in two steps 50 ms apart; options that render more than about 150 ms after the open click are not found ("combobox opened but no visible role=option elements were found"). agent-browser waits up to 2 s.
- upload refuses a directory (agent-browser passes directories for `webkitdirectory`); it reads regular files only.
- A plain non-editable element (a `<div>`) is `not_editable` for fill and type; agent-browser tries to focus it first.

Snapshots, frames and screenshots:

- `snapshot -s` with only hidden matches prints "(empty page)" (a scoped snapshot shows what the page snapshot shows), where agent-browser 0.45 fails with "No accessibility node found for selector '<sel>'".
- An iframe whose document the page cannot read (cross-origin, or a frame in its own target) shows as its Iframe line without content.
- `find`, and the locators of `get`, `is`, `wait` and the element commands (`text=`, `role=`, `label=`, ...), search only the current document (the top page, or the frame that `frame` selected), as agent-browser 0.45 does; they do not enter iframes. For an element inside an iframe, use the ref that `snapshot` prints (the snapshot walks same-origin iframes four levels deep) or select the frame with `frame <iframe>` first.
- **Frames in their own target.** WebKit with site isolation puts a cross-site iframe in its own target; agent-ios ignores non-page targets, and `frame` refuses such a frame with `unsupported`. Evidence (2026-11-26): Safari on the iOS 26.5 Simulator ran cross-site iframes, also nested ones, in the page's target with their own execution contexts: `frame`, `eval`, `check`, `find`, `wait`, `console`, `errors` and `screenshot --annotate` all worked there, so no frame target was seen and Target routing to frame targets was not built. When a future iOS enables site isolation, the refusal stays until that routing exists.
- `screenshot --annotate` labels the refs of the top document's snapshot (which includes same-origin frames); refs of a selected cross-origin frame are not labelled. Boxes of rotated or skewed iframes use the frame's bounding box; only translation and scale are exact. Labels and boxes are clipped to frame viewports only: an iframe that an overflow-clipping ancestor in its parent document cuts is not clipped further.

Diffs, states and tabs:

- **`tab keep`.** WIP has no focus emulation (Chrome's `Emulation.setFocusEmulationEnabled`), no lifecycle freeze (`Page.setWebLifecycleState`) and no setting for background throttling (checked in the protocol of iOS 16.0 to 27.3 and WebKit main: `Page.overrideSetting` has none). `tab keep live|throttled|frozen` exists and fails with the reason (exit 1, `unsupported`); Safari throttles background tabs itself.
- **`diff url` screenshots.** The pixel rule is agent-ios's `diff screenshot` rule (largest channel difference over threshold × 255), not agent-browser's Euclidean RGB distance; no diff image is written (`diffPath` is null).
- **`diff snapshot` text.** The diff marks no "\ No newline at end of file" and compares lines as split on "\n"; agent-browser's diff treats a last line without newline as different from the same line with one, so counts can differ when a change touches the last line.
- **`state`.** No encryption (`encrypted` is always false), no `state clean`, no autosave files.

Heap:

- **Snapshot size.** A heap snapshot is one protocol reply. iwdp drops a device message above 64 MiB and the direct transport one above its frame cap (default 256 MiB); a heavier page's snapshot then gets no reply, and `heap snapshot` ends at its deadline (exit 124; with the direct transport the error adds the frame cap hint). After the page connection hands over the reply, `heap snapshot` holds the snapshot only once: it decodes the string inside the reply's own memory, writes the file from there, and builds the class summary by scanning the node list without decoding it (Go benchmark BenchmarkHeapSnapshotReply50MB, synthetic 50.5 MiB snapshot: 61 KB allocated on top of the reply, against 305 MiB before). Not measured, inferred from the code: the page connection still holds several transient copies of the reply (about four, each the size of the escaped snapshot) while it unwraps a Target-routed message. JavaScriptCore returns no data for a snapshot that outgrows its string builder; the command then fails with "WebKit returned no snapshot data".
- **Summary.** By class name and self size only: no retained sizes, dominators or paths (Web Inspector computes those from the same file). Snapshots in JavaScriptCore's GCDebugging format are refused. Instances of classes with the same name are counted together.
- **Snapshot chain.** After the first `heap snapshot`, WebKit's Heap agent of the page keeps its snapshot chain until the agent is reset, which holds memory in the page; a later snapshot's JSON lists the live nodes of the whole chain. The memory cost on iOS was not measured.

CSS rules:

- `css matched`: WIP gives no style sheet headers without `CSS.enable` (which hangs through iwdp), so rules of the document's own `<style>` elements show the line inside the style element, not the document line; var() is resolved only in the element's own rules; keyframes, `@property`, `@position-try`, animation and transition styles are not shown. The inherited-property and shorthand lists are built in, so `--computed` and `css computed` with a shorthand can show a few more properties than DevTools. Checked on the iOS 26.5 Simulator and WebKitGTK 2.54 only; older iOS versions list the three methods but were not run.
- chrome-devtools-mcp's `get_css_styles` through the CDP endpoint ([cdp.md](cdp.md#client-notes)): source lines of a document's own `<style>` rules are counted inside the element; no keyframes, `@property`, `@position-try`, animation or transition styles; `env()` values are not reported (`CSS.getEnvironmentVariables` is not translated: WebKit has no command that lists them); `@container` rules show no container node.

Logpoints:

- A source-mapped logpoint is resolved once, at `logpoint add`; after a rebuilt bundle it stays on the old generated line: remove it and add it again. A logpoint added after the rebuild and a reload reads the new map. Index source maps (with `sections`) are not supported.
- Source maps: a map is read once per script of a document (a reload or navigation reads it again), and only maps of the active target's current document are candidates. A map larger than 16 MiB or with more than 2 million segments is refused ("set the logpoint on the generated script"); a page keeps at most 32 maps or 4 million segments, dropping the least recently used.
- When two loaded scripts both map an original line equally (the same original file bundled twice), `logpoint add` fails and names both scripts; give the generated script URL and line.
- An original source is found only in a script that WebKit reported after the first logpoint command on the page; when another owner (a CDP client) enabled the debugger first, earlier scripts are unknown. A path suffix that matches no known script waits for a script with that suffix ("not bound yet").
- **Pause settings.** agent-ios keeps the page from pausing only for its own Debugger state. A raw legacy call of another owner that sets `setPauseOnDebuggerStatements` true or `setPauseOnExceptions` all or uncaught afterwards wins (the latest owner's value is effective) and can pause the page. WebKit has no getter for the pause settings, so the release of the last owner does not restore an earlier frontend's value (for example Safari Web Inspector's pause on `debugger` statements): it leaves WebKit's default, no pause.
- Two logpoints that resolve to the same location cannot both bind (WebKit keeps one breakpoint per location); the second add fails. Logpoints in workers and in frames in their own target are not supported.

Private mode:

- `diff url`, the `state` group except `save` and `load`, `heap`, `css`, `logpoint` and `tab keep` print only their status line in private mode, because their results are page content (class names, style rules, logged values) or name saved states. Run the one command whose result you need with `--private=false`.

## Open device questions

Device check 3 (2026-11-09: iPhone X, iOS 16.7, Safari 16.6, iwdp 1.9.2) answered part of the questions. Every item below "Still open" needs a device run before the behavior counts as verified.

- **`cookies set`, `cookies clear` and `state load`.**
- **Touch events** (synthetic): `tap` and `swipe`.

Device check of 2026-11-11 (iPhone X, iOS 16.7.16, Safari 16.6.2, iwdp 1.9.2):

- **Network conditions** are applied, but not at the nominal rate: with `emulate network slow-3g` (50,000 bytes per second) a 100 KiB fetch took 1.0 s instead of the 2 s that the rate gives, and 0.48 s without the throttle.
- **`set offline`** fails every request of the page (`fetch` rejects with "Load failed"), as its help says; `navigator.onLine` stays `true` and no `offline` event fires, because the mode is request interception, not a network state.

Found:

- **Listing.** The empty listing comes from one broken file-descriptor slot in iwdp 1.9.2, not from a rule of iwdp ("iwdp does not list pages while a page is connected"). The trigger was not reproduced on demand.

Still open:

Deadlines and exit codes are unchanged; only a write that stalls during an action keeps the page's later commands failing for about 10 s instead of about 2 s before the connection is replaced. Seen in a test (closure review rev2-armed-detach F5), not on a device.

Not checked on a physical iOS 26 device.
