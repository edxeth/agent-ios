# Known limits

Every accepted limit of this release, with its reason. Features that iOS WebKit cannot support at all are in [synthetic-input.md](synthetic-input.md). Ids in brackets (K01, C13, ...) refer to the W1c backlog and [notes/w1c.md](notes/w1c.md).

## Ownership and connections

- **Reservations and busy hints are not locks.** A client that ignores reservations (another tool, a raw script, Safari Web Inspector) can still take a page. Reason: iwdp gives a page to the newest client, and with `--no-frontend` it reports no owner.
- **A peer-ended first attach (F13).** When another client ends the daemon's very first connection to a page, the daemon has no page state to mark lost. The next first attach is decided by the preflight busy hint only.
- **"Stalled" wording after a peer end.** A call whose own budget ended and whose probe then finds the connection ended by a peer can still report a stall instead of "lost" (exit 4 either way). `tab <id>` gives the takeover advice only when the page is already marked lost; otherwise it gives the hidden-tab advice. The CDP `Target.activateTarget` probe says "not the visible Safari tab" for any probe failure.
- **iwdp does not list pages while a page is connected.** On the second device check, the user's iwdp (1.9.2) closed every listing request on 9221 and 9224 without a reply while any WebSocket to a page was open, and answered again after it closed. Cause (device check 3): iwdp 1.9.2 can get one broken file-descriptor slot, right after the stderr pair "sendq retry failed: Connection timed out" and "recv failed: Bad file descriptor". Every connection that lands on that slot is closed without an answer; with one page WebSocket on the lowest free slot, every listing request lands on the broken one. Restart iwdp to recover: `iwdp-cli restart-iwdp` for an iwdp that iwdp-cli started; any other iwdp only whoever started it, and only when nobody else uses it: `scripts/iwdp-owner-check.sh --terminate <record>`, then `scripts/iwdp-owner-check.sh <record>` until it reports `gone`, as [Stopping an iwdp by hand](device-runbook.md#stopping-an-iwdp-by-hand) in device-runbook.md describes; otherwise ask whoever started it, or the user. Trigger (reproduced without a device): at start iwdp connects a SIMULATOR inspector to `localhost:27753` and tries each address of `localhost` in turn. When nothing listens on 27753, a `127.0.0.1` attempt is refused at once and iwdp goes on to the next address, so the order of the addresses does not matter: where `::1` is one of them and does not answer (for example IPv6 off on `lo`), the connect to `::1` stays pending, and about 133 s after each start iwdp removes it but keeps its send queue, which breaks that slot. Workaround: `-s 127.0.0.1:27753` gives iwdp one address, whose connect is refused at once. An iwdp that iwdp-cli starts (auto-start, `restart-iwdp`) passes this flag on Linux, where no iOS Simulator runs; macOS keeps the default address, which the simulator uses. For an iwdp that you start yourself on Linux, add `-s 127.0.0.1:27753` to its command line. v1.9.2 is the newest iwdp release and has no fix. Commands on attached pages keep working. Commands on a page that the daemon holds open need no listing: the session's page without `--page` (the `tab <id>` choice, else the page its last command without `--page` used), its tab id or key, or its ws:// URL. Commands that need the listing (`tab list`, `tab new`, `tab close`, `tab <id>` for a page that is not attached, `--page <title>`, another session's first command, `devices`, the CDP endpoint's page list) fail with exit 5 and advice: run `iwdp-cli daemon stop` to close the page connections, or restart that iwdp as above. The same holds when the device list answers but the page list of a device with an open page fails; a device without an open page whose page list fails is left out, as before, so it hides no other device. The daemon never takes such an iwdp for dead and never starts a second one. The commands `devices` and `status` read the listing themselves (`status` outside the daemon, `devices` in it), so they name the empty reply and its likely cause, not the open connection. `iwdp-cli status` reports the check's error with its advice ("does not answer: ..."); it starts nothing.
  - **CDP clients on such an iwdp.** The CDP endpoint reads the listing for its target list and for every target lookup (`/json/list`, a `/devtools/page/...` connection, `Target.getTargets`, `setAutoAttach`, `attachToTarget`, and others), so these fail with the same advice while the daemon holds any page connection, also one that an earlier CLI command opened. `get cdp-url` itself reads no listing when it selects a page that the daemon holds open (the session's `tab` choice, its default page, or `--page` with its tab id, label, key or ws:// URL), but a client of the URL still needs the listing for its target list. What to do: run `iwdp-cli daemon stop` (it also stops the CDP endpoint and revokes its URLs) or restart that iwdp as above, then get a new URL. Whether a CDP client can work on such an iwdp at all is not known, because its own attachment opens a page connection. Details: [cdp.md](cdp.md#when-iwdp-does-not-list-pages).
- **A command during a recovery** waits for the running background reconnect within its deadline; it never waits for a lost page, which needs `--takeover`.
- **iwdp loses the devices when usbmuxd restarts.** ios_webkit_debug_proxy 1.9.2 subscribes to usbmuxd's device events once and never subscribes again; its handler of a closed subscription does nothing, and no later upstream release changes that (upstream issue #28). Where usbmuxd exits when the last device is unplugged (Linux with `usbmuxd --systemd`), every iwdp that runs across an unplug lists no device from then on. On Linux the daemon restarts the iwdp that iwdp-cli started and recorded when it holds no usbmuxd connection any more ([guide.md](guide.md#the-daemon)); an iwdp of another user cannot be inspected and is left alone without a message; an iwdp that the user or another program started stays deaf until its owner restarts it, and the error says so. Device check of 2026-11-11: after a replug the old iwdp listed no device, and the next `tab list` restarted it and listed the tabs in 0.6 s; after another replug the restarted iwdp did not answer within 5 s and logged nothing about the device, and the command 30 s later started a new iwdp that listed the tabs.
- **iwdp drops a device when a client closes at the wrong moment.** ios_webkit_debug_proxy 1.9.2 ends its whole connection to a device when it fails to pass one inspector message (a reply or an event) to a page WebSocket that is closing or gone: `iwdp_on_applicationSentData` returns the failed send, and `rpc_recv_msg` then logs "Invalid message _rpc_applicationSentData" and closes the device connection. It never connects to that device again by itself. Device check of 2026-11-12: after iwdp ended a page connection while a reply to it was on its way, the iwdp log had that line and "Disconnected :9224 from iPhone X", and the listing stayed empty while `idevice_id -l` listed the iPhone. A raw WebSocket client reproduced it: it took a page that the daemon held, made the page log to the console every millisecond, and closed its socket with a reset; iwdp logged "send failed: Connection reset by peer", the "Invalid message" line and the disconnect. Every client that closes a page connection while the page still sends can cause it; iwdp-cli releases a page (Console.disable and the other resets) before it closes the connection, which leaves only the replies and events that are already on their way. On Linux the daemon and `devices` restart the iwdp that iwdp-cli started and recorded, at most once per 30 s ([guide.md](guide.md#the-daemon)); the device refused the first restart right after the loss, and accepted one 30 s later. Another program's iwdp stays without the device until its owner restarts it, and the error says so. In the same check, iwdp also ended the first connection of about every second attach to a page that no other client held, with no message in its log; the command fails with exit 4 and tells to run it again, which then attached. The cause is not known; it did not happen with a new iwdp in 30 attaches.
- **The 30 s start back-off lives in one daemon's memory.** Without `IWDP_NO_DAEMON=1`, the daemon is the only process that starts iwdp by itself (page commands and `devices` run in it), so its back-off after a failed start covers every automatic start of that daemon. It does not hold across processes that do not share that daemon: with `IWDP_NO_DAEMON=1` every command has its own; processes with different `XDG_RUNTIME_DIR` values have different daemons; a client of another iwdp-cli binary replaces an idle daemon, which then starts without the old one's back-off; and a daemon killed while iwdp starts leaves that iwdp running, with no lock or record, while the next start may launch another. With `IWDP_NO_DAEMON=1` every command that needs iwdp can start it again, so repeated commands repeat the start (the reviewer's check of 2026-11-12: three `devices` commands, three failed starts in 0.4 s); in the other cases the new daemon or process starts without the back-off of the one before. A second iwdp does not start while the first one owns the listing port. Accepted by the user on 2026-11-12, after a cross-process back-off file kept needing more machinery for these cases.
- **A locked device at an iwdp start.** iwdp 1.9.2 connects a device only on usbmuxd's attach event, inside its one event loop. When the device refuses the inspector connection (a locked device in the device check of 2026-11-11, logged as "Unable to connect to ..."), iwdp does not answer its listing during that attach and does not try the device again later. iwdp-cli's start then fails after 5 s, says that the device refused, and tells to unlock it; the start back-off (30 s) applies. Unlock the device before the first command. An iwdp that runs while a device was locked at its plug-in does not list that device after the unlock: unplug the device and plug it in again.
- **iwdp start (K01).** The check that port 9221 is free is a bind probe, not an atomic reservation, so a short window remains between the check and the start. On macOS `lsof` sees only this user's processes.
- **restart-iwdp on macOS.** The restart refuses unless it can read both the process start time (`ps`, one-second resolution) and the start token from the kernel's process arguments. `scripts/iwdp-owner-check.sh --terminate` (Simulator teardown, manual stop) signals on Linux through a pidfd held during its checks; on macOS it sends SIGTERM by pid right after its checks, so a process that exits and whose pid is reused in that window could get it. restart-iwdp checks and signals in separate system calls on every system.
- **A Simulator iwdp record can outlive its process.** Teardown removes setup's iwdp record only when no process has the recorded pid. When a process of another user, or one with another start time, has reused that pid, the check reports `cannot-check` or `mismatch`, teardown keeps the record, and setup refuses until that process ends; the next teardown then removes the record.
- **Record removal compares, then deletes.** `scripts/iwdp-owner-check.sh --forget` (Simulator teardown, manual stop) renames a record aside, compares its device, inode and content with what it read, and deletes it only on a match. A writer that already holds the record open can still change it in place after that comparison. scripts/sim-setup.sh and iwdp-cli replace their records by rename and never write one in place.
- **Reconnect events.** A reconnect's new connection holds at most 1024 events per subscriber until it is installed; extra queued events are dropped and counted, and a read-loop overflow refuses the connection (exit 4).
- **Idle probe (K08).** An idle probe that the client cancels resets the idle clock, so the next command within the idle period runs without a probe; its call budget still detects a hang.
- **Writes after a stall (K09).** After a stall is declared, a write that starts in a narrow window can still block until its own deadline.
- **Two daemons on one page.** The page-side release of the runtime checks the lease epoch only, not the daemon. A release from one daemon whose epoch equals the epoch of another daemon's current owner clears that owner's ref maps, and that owner's next call reports its refs as unknown. No ref resolves to a wrong element. Reason: the page runtime's release takes only an epoch (`release(epoch)`).

## Page state and cleanup

- **No reconnect only to clean up.** When a lease ends without a live connection, or its cleanup fails, page-side state stays until the document navigates: the geolocation shim, JavaScript-mode routes and dialog overrides of the current document (C18). A cleanup that is owed is sent by the next connection's setup, or by a bounded background reset after a provisional target commits.
- **Release does not undo the page.** It does not restore authentication state or undo submitted forms or transactions.
- **Profiler stop (C19).** On a stall, `profiler stop` ends at its deadline (exit 124) instead of at once with exit 4. A ScriptProfiler run left on a connection that was not attached is not marked; WebKit ends it when that connection closes, otherwise the next start stops it.
- **Back/forward cache.** Forced pseudo states and DOM node bindings of a cached document survive a restore (K06; inert without `CSS.enable`). A request paused in a cached page stays paused until restore or eviction, and a restore whose setup fails before its `Network.disable` leaves it unknown to the daemon (K05). The context list of a restored document fills one or two round trips after its navigation event; on iOS 16 nothing is replayed unless Page is enabled (K11).
- **Agent bookkeeping (K10).** Two concurrent first enables of one agent on one target can interleave their resets. Agent records of replaced targets stay for the life of the connection.
- **Breakpoints.** A breakpoint set that crosses a provisional commit can fail with a target-swapped error; a retry succeeds (K07). The breakpoint id recorded for a target that was destroyed can stay in the desired state until the next setup replaces it.
- **Debugger pauses.** A pause that arrives after a release ended its lease is not drained. A release that cannot resume every paused target names them in its error. Pause records stay until their target is destroyed.
- **Node ids in the main document.** A command that looks up a node id and then sends it (`hover --css`, `highlight`, a screenshot of a ref) has no target fence in the main document. When a provisional target commits between the lookup and the send, the node id goes to the new document, where it can name another node or none. Reason: only a frame scope (`frame <iframe>`) pins the sends of a command to the target that reported its execution context; inside a frame such a send is refused instead.
- **Frame cleanup wait.** A frame whose page-side state an earlier lease left is counted as gone only on a complete context inventory of the current target (Runtime known to be enabled there). Until then the frame stays recorded, and each runtime command of the new lease waits for the frame's report again, at most 250 ms and half of its 1 s cleanup budget, until the inventory is complete or the lease release runs. Reason: a frame that the inventory does not list yet can still exist and hold state.
- **Network gaps (K02, K03).** A gap in the network log starts when the old connection was retired; events that a stalled connection never delivered before that are outside the gap. When the old frontend's close already reset Network and the new setup sent no `Network.disable`, the gap is reported only by a later connection that sends one.
- **Refused intercepted requests (K04).** A request that WebKit took and then refused (decode error, finished loader) stays unanswered inside WebKit.
- **Safety net (K12).** Tombstones of removed interception rules end with the lease: a provisional target that refused a rule's removal and commits after the release keeps the rule. A rule that a provisional target kept after it refused a removal that the daemon sent itself (for example a lease release) has no tombstone either. In both cases the safety net answers the rule's requests, so no request stays paused.

## Explicit ws:// URLs (C13 to C16)

Pages opened by an explicit `ws://` URL that is not an iwdp device page (`--page ws://...` for a local endpoint) still use the older connection type (`webkit.Client`). Reason: moving it onto the session layer changes the target-wait rules under every mock test that opens such a URL, so it needs its own change. Such pages have no agent resets of unknown backends (C14), report no source target for events (C15), and do not replay execution contexts after a back/forward cache restore, so `frame` after such a restore fails with an actionable error (C16). Such a connection has no agent states, so its context inventory never counts as complete, and a frame release there never decides that a frame is gone: the frame stays recorded.

## Features and platforms

- **Pause-on-start is best effort.** "Runs before page scripts" (dialog override, init scripts, error hooks, JavaScript routes, the CDP page compatibility shims) is partial when WebKit refuses pause-on-start or does not answer within 1 s. On iOS 16.7 through iwdp it probably works (device check 3, an inference: see "Open device questions").
- **document.cookie keeps deleted cookies.** In an open page, `document.cookie` still returns a cookie that WebKit deleted (an expired `Page.setCookie`, `cookies clear`), also after a reload and after a cross-site round trip, while the server and `Page.getCookies` no longer see it (device check 3, iOS 16.7). A non-expired `Page.setCookie` of the same cookie does update `document.cookie`. Inference: the web content process keeps a cookie cache that is not told about the deletion. Workaround: a page-side `document.cookie = "<name>=; expires=Thu, 01 Jan 1970 00:00:00 GMT; path=<path>"`.
- **Playwright locators on Safari below 17.4.** Playwright's locator actions, `getByRole` and `ariaSnapshot` call `Element.prototype.checkVisibility`, which Safari 16.6 (iOS 16.7) lacks; the CDP endpoint installs a shim for it, and Playwright's popover and `getHTML` features still fail ([cdp.md](cdp.md#page-compatibility-shims)). With the shim, device check 4 (iOS 16.7, code a8aec70) passed Playwright's `getByRole` click, `getByLabel` fill, a locator read and `ariaSnapshot`.
- **One ScriptProfiler recording per page.** `profiler start`, `trace start` with the `script` category (the default categories are `timeline,script`) and a CDP client's `Profiler.start` all use WebKit's one ScriptProfiler run of the page. While one of them records, a second start is refused and names what to do: stop the recording that holds the run (`profiler stop`, `trace stop`), or start the trace with `--categories timeline`. To trace and profile at the same time, record a Timeline-only trace (`trace start --categories timeline`) beside the profiler. Reason: WebKit runs at most one ScriptProfiler run per page, and a second `ScriptProfiler.startTracking` starts nothing, so the second recording would silently share the first one's samples.
- **CSS through iwdp.** `CSS.enable`, `CSS.getAllStyleSheets` and `CSS.getStyleSheetText` hang through iwdp and are refused; `hover --css` therefore fails there.
- **Not verified on a device:** see [Open device questions](#open-device-questions).
- **Storage quota.** `state load` and `state save` refuse a storage area above 90% of the 5 MiB quota in WebKit's count; strings that page script stored as 16-bit can count less than WebKit counts.
- **`diff screenshot`** compares viewport screenshots only. **`vitals`**: LCP, CLS and INP need Safari 26.2 or later.
- **`click --new-tab`.** When the page changes between the readiness probe and the gesture call, the page can hold a transient user activation although no tab opened.
- **Direct transport.** Results above the frame cap (default 256 MiB) need chunked messages, which are not supported: use `--transport iwdp`. On iOS 17 and later it may need a tunnel; until a device run passes, `auto` never chooses it.
- **CDP.** The endpoint serves the methods of the table in [cdp.md](cdp.md#method-table) and answers every other method with "wasn't found"; [cdp.md](cdp.md#limits-per-domain) lists the limits per domain and what each pinned client loses. The compatibility suite runs only on WebKitGTK. An endpoint under `IWDP_NO_DAEMON=1` ends with its process.
- **Whitespace text in the CDP accessibility tree.** `Accessibility.getFullAXTree` has a StaticText node named " " for each whitespace-only text node between elements, which Chrome leaves out. Clients show them: chrome-devtools-mcp's `take_snapshot` lists them as lines such as `uid=1_3 " "`, and Puppeteer's `accessibility.snapshot()` as extra StaticText leaves. The elements, their names and their uids or refs are not affected. Reason: the endpoint builds the tree from the runtime's snapshot walk (internal/runtime/js/40-snapshot.js), which collapses such text to one space and keeps it.

## Open device questions

Device check 3 (2026-11-09: iPhone X, iOS 16.7, Safari 16.6, iwdp 1.9.2) answered part of the questions. Every item below "Still open" needs a device run before the behavior counts as verified.

Confirmed on iOS 16.7:

- **Interception through iwdp.** CDP `Fetch`: an awaited `fetch` that Puppeteer's request interception or Playwright's `page.route` fulfilled returned in 175 ms and 140 ms; the CLI's `network route` fulfilled too.
- **ScriptProfiler.** `profiler start` sampled (1,133 samples in 2 s), and `trace start` with the `script` category recorded Timeline and script events.
- **Cookie delete.** An expired `Page.setCookie` deleted exactly the cookie of that name, domain and path, as the server saw it: its namesake of another path stayed, and the `Page.getCookies` right after it listed only that namesake. CDP `Network.deleteCookies` with a path did the same. `document.cookie` in the open page does not show the deletion ("document.cookie keeps deleted cookies").
- **Large sources through iwdp.** Playwright's 344,936-byte `Runtime.evaluate` passed through iwdp whole, so it needs no staging there.
- **`cookies set`, `cookies clear` and `state load`.**
- **Touch events** (synthetic): `tap` and `swipe`.
- **Pause-on-start, probably** (an inference): across about 15 attaches the daemon logged no refusal or timeout of `Target.setPauseOnStart`, and an init script ran at `readyState` "loading" before any page script after two cross-site navigations.
- **CDP clients.** agent-browser (both builds), Puppeteer and chrome-devtools-mcp pass their scenarios. Playwright's goto, evaluate, screenshot and `page.route` pass; its locator actions failed without the `checkVisibility` shim ("Playwright locators on Safari below 17.4"). Device check 4 (code a8aec70) ran Playwright's scenario with the shim: all 15 steps passed, the locator steps included.

Device check of 2026-11-11 (iPhone X, iOS 16.7.16, Safari 16.6.2, iwdp 1.9.2):

- **Network conditions** are applied, but not at the nominal rate: with `emulate network slow-3g` (50,000 bytes per second) a 100 KiB fetch took 1.0 s instead of the 2 s that the rate gives, and 0.48 s without the throttle.
- **`set offline`** fails every request of the page (`fetch` rejects with "Load failed"), as its help says; `navigator.onLine` stays `true` and no `offline` event fires, because the mode is request interception, not a network state.
- **History moves.** A `forward` sent at once after a `back` across a cross-site navigation started no navigation in 2 of 5 runs, without an error, and a `forward` sent 50 ms later moved in each of 4 runs. `back` and `forward` do not ask for the move again, because a move that WebKit accepted but has not started yet would then move twice: they end with exit 3 and tell to check the URL and run the command again.

Found:

- **Listing.** The empty listing comes from one broken file-descriptor slot in iwdp 1.9.2, not from a rule of iwdp ("iwdp does not list pages while a page is connected"). The trigger was not reproduced on demand.

Still open:

- **Listing.** Whether a CDP client can work on an iwdp with the broken slot.
- **Pause-on-start.** Whether iwdp relays the reply of `Target.setPauseOnStart` on iOS 26, which may hold it; the inline `confirm()` of a new document was not run.
- **Oversized sources.** iwdp's upper limit to Safari (64 MiB as configured, not probed); the direct transport's (go-ios frame limit 16 MiB) with Playwright's injected script; and whether a staged evaluate works on iOS 16.7 on a page whose Content-Security-Policy forbids eval.
- **Cookie delete.** The namesakes of the parent domain and of the other kind (host-only or domain cookie).
- **ScriptProfiler.** CDP `Profiler` and traces with V8 categories through a CDP client.
- **Interception.** The WIP rule texts with the bridge's NUL suffix on current iOS, and the interception of a cross-process navigation's document request through iwdp.
- **Not reached by device check 3:** `set credentials` (enabled on WebKitGTK only), the direct transport, a second inspector moving the lease to lost, the busy hint with iwdp's frontend on, `diff screenshot`, `click --new-tab`, `frame` on a cross-origin iframe, and `wait --url` across a target swap.
